应该补两张“回溯任务卡”，但不应该把验收写成“已通过”。
一句话理由：你能确认的是“实施已经发生”，不能倒推出“当时已经验收”，所以卡片应明确写成“实施完成 / 回溯补记，正式验收未执行（或待复核）”，记录现有代码、文件和运行状态作为证据，真正验证后再补验收结论。
最合适的状态语义是：
YAMLimplementation_status: completedacceptance_status: pendingrecord_type: retrospective
如果现有任务卡只能有一个 status，就用：
YAMLstatus: done
但正文必须明确：

done 仅表示历史实施工作已完成，不代表正式验收通过；验收状态：待复核。



不应该每次 commit 都同步 Obsidian；应该采用“知识语义发生变化时触发更新”。
一句话理由：代码仓负责高频实现历史，Obsidian 负责稳定知识，如果逐 commit 双录必然失控；只有当改动改变了“以后维护者需要知道的事实”时才更新知识库。
可直接执行这条触发规则：
需要更新 Obsidian：


服务边界、目录结构、端口、部署方式发生变化；


新增/删除一类配置或改变配置职责；


alias / route / channel 的规则或语义变化；


primary / backup / fallback 策略变化；


引入、废弃重要模块或机制；


做出值得长期保留的架构决策 → 新增/更新 ADR；


一个重大建设阶段结束 → 更新“建设与演进记录”；


Agent 的操作前提或维护规范发生变化。


不需要更新 Obsidian：


新增一个普通模型；


调整某个模型具体 route；


某渠道 quota / health 状态变化；


bugfix、重构内部函数、改日志；


普通参数调整；


不改变系统知识模型的日常 commit。




换成一句最好记的团队规则就是：

Git 记录“代码发生了什么”，Obsidian 记录“系统现在是什么、为什么这样、以后应如何维护”。

所以你这次落地时，建议同时收紧两个边界：暂不动 projects.yaml schema；从 search_gateway 开始，新的人工任务卡正式回归 D:\Work，停止工程库与 Work 双写。
