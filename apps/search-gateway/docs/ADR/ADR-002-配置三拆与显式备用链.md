# ADR-002：采用配置三拆与显式备用链

## 状态

Accepted

## 背景

旧设计存在：

- 多渠道智能轮动
- fallback 隐式（未声明渠道自动接管）
- 产品目录、路由、渠道状态职责耦合在单一配置
- 执行路径不够可预测、难审计
- 用户请求可能经过多层轮动，日志无法复现实际调用渠道

## 决策

配置拆为三份：

1. `model_catalog.json` —— 产品目录 / alias / 展示（"是什么"）
2. `model_routes.json` —— primary / backup / fallback（"去哪里"）
3. `channel_registry.json` —— 渠道状态 credential 引用 / quota / health（"渠道怎么样"）

新增实现：`catalog_routes.py`（catalog + route 的加载、解析与路由逻辑）

路由策略调整为：

- **默认单渠道单模型**（确定性路由）
- **显式 primary / backup / fallback**（备用链需显式声明）
- **`fallback_policy.enabled=false` 默认**，仅单模型显式开启

## 核心原则

- catalog 管"是什么"
- routes 管"去哪里"
- registry 管"渠道怎么样、凭证是否有效"

## 被废弃的机制

- 多渠道智能轮动作为默认行为
- 隐式 fallback
- 未声明渠道自动接管请求

## 备选方案

### 保留智能轮动
为什么否决：执行路径不可预测、无法审计、故障链不清，与个人/小团队网关的运维成本不匹配。

### catalog 与 routes 合并
为什么否决：产品目录（用户可见契约）与路由（技术实现）职责不同，合并后改路由会引起展示变化。

### route 与 channel 合并
为什么否决：路由（怎么走）与渠道资源状态（现在的状态）不同，渠道状态是运行态、路由是配置，混写会让服务自改事实源。

### 一步彻底删掉 fallback
为什么否决：会失去免费池 / SLA 场景的生命线；改为显式备用链（保留逃生门、去掉隐式轮动）。

## 后果

正面：
- 可预测
- 可审计
- Agent 易理解
- 故障链清晰
- 热重载（mtime 感知 + 原子替换）无需重启

代价：
- 配置项增加
- 新模型需要显式维护 route，不能自动"进流量"

## 迁移要求

- 新渠道登记 channel_registry.json 后**不自动获得流量**，仅被 model_routes.json 显式引用后进入路由。
- 新增模型顺序：catalog → routes → 确认渠道在 registry → 验证闭环。
- 改变路由语义前必须阅读本 ADR。
