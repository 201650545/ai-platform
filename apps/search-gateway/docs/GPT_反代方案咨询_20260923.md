# GPT 镜像咨询：网页反代项目与网关接入架构（2026-09-23，Thinking 档）

> 提问背景：3100 网关 + 自研 3102 浏览器桥（千问/MiMo）。GPT 结论：A 独立 adapter 为主 + C 浏览器桥降级为执行后端 + B 网关特判不做。

## GPT 回答

结论先给：**你的 3100 网关应该选 A 为主、C 作为少数平台的降级后端，B 尽量不要做。** 也就是把“网页版逆向/浏览器会话”全部隔离在独立 provider-adapter 服务里，对外统一暴露 OpenAI-compatible API；3100 只负责渠道注册、成员回落、额度、熔断和路由，不知道 cookie、网页 RPC、DOM、WAF 这些细节。

## 问题 2：你这套系统的最优架构

我的架构结论是：

**3100 = 稳定的 control/data plane 网关**

→ **官方 API 渠道：直接转发**

→ **Web provider：独立 Adapter 服务**

→ 只有 adapter 内部自己决定采用
`direct reversed RPC → browser-backed fetch → unavailable`

不要让 3100 知道 Qwen 的 sessionId、Kimi 的 RPC protobuf、Gemini 的 cookie 或页面结构。

**仅作为必要 fallback**

这里“封号风险隔离高”并不是说不会封号，而是 **事故 blast radius 小**：一个 provider 的 session 被打掉，不会污染网关进程和其他渠道。

### 推荐你实际落成这样

```
                         ┌─ official-openai                         ├─ dashscopeclient  │                      ├─ moonshot-api  ▼                      └─ volcengine:3100 gateway  │  │ OpenAI-compatible only  │  ├── :3110 qwen-web-adapter  │       └─ direct Web RPC  │  ├── :3111 kimi-web-adapter  │       └─ Connect RPC / supported web session  │  ├── :3112 gemini-web-adapter  │       ├─ reversed RPC  │       └─ browser worker fallback  │  └── :3102 browser-worker-pool          ├─ Chrome profile A          ├─ Chrome profile B          └─ ...
```

关键是 **`:3102` 不再直接承担 OpenAI compatibility**。

它应该降级成一个内部的 **Browser Execution Backend**：

```
provider adapter     ↓browser RPC     ↓3102     ↓existing Chrome session
```

这样网页 DOM、JS fetch、cookie、页面变化只影响对应 provider adapter。

* * *

### 3100 和 adapter 之间的契约也要刻意做窄

我建议每个 adapter 至少统一：

```
GET  /healthGET  /v1/modelsPOST /v1/chat/completionsPOST /v1/responses      # 能做就做
```

网关只理解：

```
base_urlapi_keymodelsweightprioritydaily_quotahealthconcurrency_limit
```

然后增加几个 **channel capability**：

```
streamtoolsvisionweb_searchreasoningfile_uploadbrowser_backed
```

不要写：

Python

```
if channel.type == "qwen_web":    ...elif channel.type == "kimi_web":    ...
```

而应该还是：

Python

```
forward(channel.base_url, normalized_request)
```

这正好保住你现有 `custom_channels` 热添加模型。

## 你的 C 浏览器桥，建议保留，但改变定位

你现在“日常 Chrome 页面上下文 fetch → OpenAI SSE”的方案，**技术上其实走对了一半**。

真正的问题不是 browser automation，而是它目前同时承担：

**认证 + WAF 环境 + provider 协议 + OpenAI 协议转换。**

职责太多。

拆开以后，让 Chrome 只提供：

```
execute_fetch(origin, request)
```

或者更高一级的：

```
qwen.send(...)gemini.send(...)
```

而 OpenAI SSE 拼装、错误翻译、model mapping、conversation mapping 都在 adapter 中完成。

好处非常现实：

网页改一个字段：

```
只发 qwen adapter
```

而不是：

```
改 3100 → 整个聚合网关重启
```

* * *

## 并发方面：浏览器桥不要假装它是普通 HTTP upstream

HTTP 逆向 API 可以：

```
50 / 100 / 500 concurrent
```

一个真实网页登录 session 通常不能这么规划。

浏览器型 provider 更合理的是：

```
account/profile      │      ├── semaphore      ├── request queue      └── rate limiter
```

而不是把 50 个请求同时灌进同一个 Chrome profile。

也就是说你的成员回落链可以很好地复用：

```
qwen-web-01  concurrency=2qwen-web-02  concurrency=2qwen-web-03  concurrency=2        ↓qwen-official-api
```

这样 **Web 渠道是 opportunistic capacity，不是 SLA capacity**。

这个设计我非常建议。

## 哪些平台值得做

从纯工程角度：

**Qwen：可以保留。** 现成逆向项目多，当前协议还相对容易抽象，优先 direct adapter；你的 Chrome bridge 仅 fallback。`encryptarun/qwen-api` 就是比较好的参考。[GitHub](https://github.com/encryptarun/qwen-api?utm_source=chatgpt.com)

**Kimi：自用实验可以。** 但协议已经出现 refresh-token → Connect RPC 变化，所以一定独立 adapter，不要并入网关 core。[GitHub](https://github.com/xiaoY233/Kimi-Free-API?utm_source=chatgpt.com)

**Gemini：技术上最适合“direct adapter + browser fallback”。** 因为社区项目已经实际遇到 browser-gated RPC；纯 HTTP 和真实 Chromium 两层都保留很合理。[GitHub+1](https://github.com/lesterppo/hermes-gem-pw?utm_source=chatgpt.com)

## 哪些我会直接从生产候选里删掉

第一是 **ChatGPT 网页版 → API**，尤其是拿消费者 ChatGPT session 做账号池、共享或商业流量。

这不只是“可能不稳定”。OpenAI 当前使用条款明确禁止自动/程序化提取服务中的数据或输出，以及绕过速率限制、限制和保护措施。[OpenAI+1](https://openai.com/policies/row-terms-of-use/?utm_source=chatgpt.com) 所以如果你的目的是真正生产使用，直接用官方 API 渠道，不值得维护 Web adapter。

第二是 **豆包网页消费者账号 → 商业 API 服务**。这个边界甚至更明确。豆包 2026-06-01 生效的用户协议授予的是个人、可撤销、不可转让、非商业使用权，并明确限制未经授权的镜像、抓取、反向工程和第三方工具干预；其付费协议也限制把服务权益拿来营利、转让或用机器人/爬虫等方式获取权益。[Doubao+1](https://www.doubao.com/legal/terms?utm_source=chatgpt.com)

所以豆包我会归类成：

**本地研究测试可以观察，商业网关 / 多用户共享 / 对外售卖：不要设计进去。**

至于 Kimi/Qwen/Gemini，我也不会把“网页套餐转 API 再对外销售”作为架构目标。即使某个项目今天能跑，项目 README 自己往往也明确标注仅供自用/研究，并提示封禁风险。Kimi-Free-API 和 Qwen-Free-API 都是这种定位。[GitHub+1](https://github.com/lxtqq/kimi-free-api?utm_source=chatgpt.com)

## 最后压缩成一句设计原则

**官方 API 是 capacity，网页逆向是 best-effort fallback；Web→OpenAI 的复杂性放在独立 adapter，绝不能污染 3100。**

如果是我接你现在的代码，我会演进为：

**A 80% + C 20%，B 0%。**

3100 保持现在这种很干净的：

```
base_url + keycustom_channelsfallback chainquota guardhealth/circuit breaker
```

而新增一层：

```
web-adapters/  qwen/  kimi/  gemini/
```

其中 adapter 可以换实现，但对 3100 永远都是一个普通 OpenAI 渠道。这样一年以后无论 Qwen 改 WebSocket、Kimi 再换 RPC、Gemini 强制 Chromium，你的核心网关都不用跟着重构。

ChatGPT can make mistakes. OpenAI doesn't use vip-24|2026-10-23 11:04:27 workspace data to train its models.
