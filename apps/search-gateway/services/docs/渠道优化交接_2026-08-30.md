## 三、GPT 最终方案（按此实施）

### 1. 渠道选定（engines.py ENGINE_ORDER + content_pool.py 默认）
- **默认** = `["metaso","perplexity","yuanbao","grok","aihot","hackernews","rss"]`（4 网页 + 3 资讯：aihot 中文 AI 日报、hackernews HN 头条、rss 科技/安全 RSS——信息全面 + 渠道失效时资讯兜底）
- **深度** = 默认 + `["zai"]`
- **full** = 8 路手动（`engines` 参数显式传）
- doubao/kimi/qianwen 降级（不入默认）
- 资讯 provider 实现：`content_pool.py` 的 `aihot_search/hackernews_search/rss_search`（独立 HTTP，不占浏览器线程），source_type = ai_news/hacker_news/rss_news

### 2. 总结触发重构（content_pool.py run_search）
- record 状态统一：`STARTED → SENT → ANSWERED`；终态 `EMPTY / ERROR / TIMEOUT`；**正文 ≥80 字才算 ANSWERED**
- quorum：默认 4 路 `quorum=3`，`soft=75s`（达到 quorum 再等 10s 补尾路）；深度 5 路 `quorum=4`，`soft=120s`；统一 `hard=130s`
- **改法**：worker 线程写共享 `records`（dict，加锁），主线程 `wait()` 检查 quorum/deadline，**不再逐线程 join**；退出时未到终态的标 `TIMEOUT`；`llm_summarize` 只收 ANSWERED
- 伪码：
  ```
  while now < hard_deadline:
      if answered >= quorum and now >= soft_deadline: break
      sleep(1)
  mark_running_timeout(); summarize(answered_records)
  ```

### 3. 插件 hub-web-search 改法（~/.dsh/profiles/web/node_modules/hub-web-search/index.js）
- record 固定字段：`engine / status / answer / urls / elapsed / error / source_type`
- 过滤空回答/过短；URL 规范化去重
- `content` 首行注明「成功 x/n，失败：渠道名(原因)」——避免模型误以为全量
- summary 失败 → fallback 为成功渠道回答拼接；0 成功 → 返回结构化 error 而非空内容

### 4. 资讯 provider（aihot）
- 做**独立 provider**（不占浏览器线程）：`GET aihot.virxact.com/api/public/items?mode=selected&since=...`（需带浏览器 UA，否则 403）
- 仅「AI 新闻/发布/融资/今日热点」等意图自动加入；普通搜索默认不混
- 转标准 `ANSWERED` record，`source_type=ai_news`，保留标题/日期/URL
- 与网页结果共同送 summarizer；支持显式 `engines=["kimi","aihot"]` 或 `engines=aihot`

## 七、渠道失效自动检测与修复闭环（2026-08-30 用户设计）
原理：渠道失效多因网站改版/DOM 变化，Open CLI 能真实看到浏览器页面 → 天然是"改版探测器+修复器"。渠道不可能全部同时失效，逐渠道检测修复即可。

**检测**：
- 每次 `run_search` 完成后，扫描 records：`status != ok` 或 `answer 长度 < 80` 的渠道 = 疑似失效
- 疑似失效写入台账 `data/search_gateway/engine_failures.json`（字段：渠道id / 首次失败时间 / 连续失败次数 / 最近错误 / 状态 open|fixing|fixed|failed）
- 连续失败 ≥2 次才触发修复（避免单次抖动误触发）；连续成功 2 次后台账清除

**修复（触发"修复 Agent"，用 opencli 操作）**：
1. `opencli browser <session> open <site_url>` 打开失效站
2. `state` / `eval` 观察当前页面真实 DOM（输入框、发送按钮、结果提取器的现状）
3. 对比 `engines.py` 里该渠道的 `fill_selector/submit/extract_js/probe_js`，按新 DOM 更新选择器
4. 重测该渠道：`engines.ask_engine(eid, 测试问题)` 验证 status=ok 且有实质回答
5. 成功 → 台账标 fixed；失败 → 标 failed 并上报用户（不盲目反复试）

**触发方式**：脚本 `detect_and_fix.py`（网关侧检测→调 opencli 修复），或由搜索网关在失败台账非空时提醒人工/Agent 触发。修复判断用 :3100 免费模型辅助定位新 DOM（不需要时纯看浏览器结构即可）。

**边界**：不自动改选择器结构之外的逻辑；修复失败立即上报，不无限重试。
