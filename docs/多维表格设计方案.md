# 飞书多维表格 · 初步设计方案

> 版本：v0.1 初稿（2026-08-10）
> 定位：AI 自助资源运营体系的数据中枢，方案书 §3 数据层的落地设计
> 状态：**待高级 AI 问诊审表设计 → 定稿 → 在飞书 base 落地**
> 背景：现有飞书 base 已有「工具资产明细表」（8 字段 10 条记录），本方案在保留它基础上扩展为 4 表体系

---

## 一、设计原则（4 条）

1. **AI 可读可执行**：每条资源都带 endpoint / models / exec_type，AI 读表即知「怎么用」，不用人再解释
2. **凭证不出表**：表里只有凭证 ID（引用），值存本地 `config/credentials.json`
3. **状态驱动**：每条资源有 `status`，调度器只消费 `status = 可用` 的行，绝不碰失效行
4. **一次登记、终身使用**：新资源按字段模板登记，全字段齐备，不靠人补说明

## 七、表间关系

```
账号资产汇总（表1） 1 ──< 免费资源大汇总（表2）   ← 关联账号
免费资源大汇总（表2） 1 ──< 自动化任务日志（表4）  ← 关联资源ID
工具资产明细表（表3）    独立，暂无关联
```

- 表 2「凭证ID」若本地有对应键，且表 1 有该平台账号 → 调度器可取
- 表 4 是「谁对表 2 做过了什么」的审计痕迹

## 八、视图设计（AI 看板）

| 视图 | 过滤条件 | 用途 |
|------|---------|------|
| 可用资源 | 表2 状态=可用 | 调度器首选 |
| 待验证 | 表2 状态=待验证 | 周期1 待办 |
| 待永涛登录 | 表1 登录方式≠已登录 | 一次性处理清单 |
| HTTP 可直接调度 | 表2 调用方式=HTTP_REST & 状态=可用 | 最快可跑通的资源 |

---

## 九、与执行层对接点

- **调度器**：读表2（status=可用 & exec_type=HTTP_REST）→ 取 resource_id → 本地 credentials.json 取密钥 → 调用 → 即时累计
- **Open CLI**：调研/验证/领取结果回写表2 状态 + 表4 日志；抓额度回写表2「已用/剩余」
- **长期监控**：定时扫表2 额度列 → 状态翻转（可用→额度耗尽）
- **数据桥**：feishu-data-hub 导出 4 表 → GitHub Pages JSON → 高级 AI 读

## 十、待高级 AI 审的问题（并入问诊包）

1. 4 表够吗？「密钥池」（同模型多厂商轮换）要不要拆独立表？
2. 字段类型（单选 vs 多选 vs 关联）对 AI 读取是否最优？关联字段导出 JSON 时会不会难解析？
3. 表2 字段是否真的「够可执行」？有没有该有而没有的（如限速、并发）？
4. 表4 日志结构能否支撑「避免重复验证」的闭环？
5. 有没有更简单的表结构，能让 AI 自取更顺、人维护更少？
