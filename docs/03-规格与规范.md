## 二、命名原则（human-facing vs machine-facing）

> 依 RFC §2.5 / §3.4b。按用途分类，**并非机械地保留或删除英文**。

| 类 | 原则 | 示例 |
|---|---|---|
| **人看层**（笔记 / 文档 / 看板 / 目录名 / 展示文案） | 中文命名 | 任务看板、资产清单、运行手册、`04_任务卡/` |
| **机器路径**（代码路径 / 文件 slug / GitHub 分支与 URL） | 依平台 ASCII 限制作英文/pinyin，**不因美观重命名** | `integrations/feishu/`、`04_任务卡/task_001` |

- 已有英文机器路径是史实与平台约束，不为了「看起来更像中文」而改名，避免破坏引用与脚本。
- 新增命名先判「给谁看」再定语文；两者都是 `[[]]` 可链的对象。

## 四、网关规格（机制，不含值）

- **端口面**：
  - `:3000` — 聚合**搜索**：多引擎浏览器会话提问抓答 → 汇总 + 总结返回（供 AI 客户端 `web_search` 引用）。
  - `:3100` — **API 转发**：统一模型组的模型调用入口（编排后调用）。
- **渠道**：渠道定义集中在网关 `channels`（`custom_channels` 自定义 + `builtin` 内置）配置；选哪些渠道、组合由该配置与运行参数决定，本节不抄写具体渠道 key / prefix。
- **统一模型 chain（`unified_models` / `routing`）**：机制 = 把可用模型编排为统一模型组，调用侧经 `:3100` 按 `routing` 规则选择实际渠道；Owner = 网关实现与配置。执行细节以网关实际配置与模块 README 为准。

- 组件事实以模块内 `组件规则卡/` 与组件代码为准；编排执行任务走 `04_任务卡/`。

## 六、飞书管线规格

- 位置：`integrations/feishu/`。
- 机制：飞书多维表格 →（单仓多项目同步）→ `public/projects/<slug>/` 静态 JSON → **GitHub Pages** 公开站点，AI 工具可无账号读取。
- 接入新项目与维护按 `integrations/feishu/` 的 README / `docs/ONBOARDING.md`，不在此复制。
- 安全：只导特定视图、字段白名单、双重安全扫描；安全故障中止部署（不在此赘述细节）。

## 七、平台主干架构摘要

> 旧 `ARCHITECTURE.md` 主干合并为本节。**本节是摘要**；完整拓扑与数据流以各模块 README 为准。

- **中央平台（`00_中央平台/`，约 `:8000`）**：导航面板 / 网关注册 / GitHub 管理 / 飞书同步，FastAPI `server.py` 提供内部 API（网关注册、GitHub、飞书、统计）。
- **网关实例（`config/` + 网关能力）**：按网关注册登记多套，聚合对外，`/api/gateways` 等注册与发现走中央平台。
- **GitHub 管理**：`github_manager.py` 封装常见仓操作（供平台与自动化使用）。
- **飞书同步**：`feishu_sync.py` 将飞书 Base 数据导出为静态数据，落入 `integrations/feishu/` 管线。
- 数据流全景：`TOPOLOGY.md` / `项目简述.md` 为历史快照，**统一以 [[docs/00-项目总览.md]] 与各模块 README 为真源**。
