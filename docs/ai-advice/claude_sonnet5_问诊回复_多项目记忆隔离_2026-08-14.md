结论（总评）

现有设计（单文件 STATE + 单写者整体重写 + 全局 8 条完成窗口）是为单项目场景优化的，核心假设是"同一时刻只有一条逻辑主线在推进"。一旦并行到 3 个项目，这个假设被打破，问题不是"要不要隔离"，而是隔离粒度要跟着"读写模式"走：

STATE 是快照类文件——每次会话开始都要整页读，且靠"单写者整体重写"维护一致性。这类文件的隔离矛盾最尖锐（写冲突、预算挤占），需要物理拆分（方案 B）。
DECISIONS / CHANGELOG 是日志/流水类文件——append-only、低频写、按需检索，从不要求"一次性读完"。这类文件用标签 + 脚本过滤即可解决归属问题，物理拆分反而是过度工程。

所以我不建议在方案 A/B/C 里三选一整体套用，而是STATE 用 B 的逻辑（索引页 + 分项目页），DECISIONS/CHANGELOG 用 A 的逻辑（打标签 + 极简脚本过滤）。方案 C（完全目录化）留作项目数进一步增长（5-6+）或项目间彻底解耦时的下一站，现在上是过度设计。

五个问题的直接回答
1. 混乱诊断

在当前全局单页机制下，3 项目并行会在这些场景出问题：

写覆盖风险：STATE.md 是"单写者+整体重写"。A 读取→本地编辑→push 期间，如果 B 已经先 push 了对课件/教学条目的更新，A 的"整体重写"如果不是严格基于最新 diff 而是凭本地理解重建全文，很容易在合并时把 B 刚加的进行中条目当作"不认识的内容"漏掉或误判为可精简项——尤其在 ≤60 行的硬预算压力下，agent 有"顺手精简"的动机。
全局 8 条已完成窗口被挤占：这是最直接的例子——A 完成 3 项、B 完成 3 项，C 的 2 项已完成条目就可能因为窗口只有 8 个位置而被提前归档，即便对 C 来说这些条目还很"新"。
CHANGELOG 检索成本线性增长：B 想看课件项目的最近进展，必须在混合了记忆系统/教学操作的流水里 grep，且没有结构化标签，只能靠关键词猜。
决策归属模糊：C 接手课件项目读 DECISIONS.md，看到的是一条条不带 scope 标记的决策，无法快速区分"按需调度、不搭定时平台"这类全局原则和"课件用某模板"这类项目专属约定，存在两种误用风险：误把项目决策当全局套用，或者反过来把全局决策当噪音跳过。
S-ID 计数器隐性竞争：格式 S-YYYYMMDD-NN 的 NN 是全局共享的，如果两个项目的 agent 在同一天各自新增条目，谁拿到 NN=03 需要靠"看到最新 STATE 才知道"，本质上是把不相关项目的写操作耦合到了同一个计数器上。
STALE 判断跨项目噪音：课件项目暂停两周不动，教学/记忆系统每天更新，全局时钟下课件条目会持续报 STALE，造成"活跃项目的复核视野"被不活跃项目的噪音污染。
"新项目单元读 STATE+DECISIONS"协议失效：随项目数增加，"一页纸"读到的 2/3 内容跟当前 agent 无关，既浪费上下文，也增加把别项目进行中条目误认成本次任务范围的风险。
2. 隔离粒度：三档怎么选
方案	本质	解决写冲突吗	解决预算挤占吗	适用规模
A（打标签）	单文件不变，加前缀/分组	不解决——仍是同一文件同一写者路径	不解决，除非引入子预算（那就复杂到接近 B 了）	1-2 项目、极少并发写的过渡期
B（索引+分页）	STATE 拆成 索引页 + 每项目一页	解决——不同项目写不同文件，git 层面天然无冲突	解决——预算下沉到每个项目页独立计算	3-6 项目，当前场景的最佳匹配
C（完全目录化）	每项目一整套 STATE/DECISIONS/CHANGELOG	解决，且连 DECISIONS/CHANGELOG 的标签维护成本也省了	解决	项目数持续增长(6+)、项目间几乎零交叉可见性需求

当前 3 个项目并行，且彼此还共享一些全局原则（按需调度等），说明还需要"轻量的跨项目可见性"，方案 C 会让这种可见性变成要写脚本汇总多目录的额外工程；方案 B 刚好在"物理隔离写冲突"和"保留全局视野"之间平衡，是当前规模的最佳落点。

3. S-ID 与 hook 适配

利：即时可辨认归属、支持独立计数器（不同项目各自的 NN 互不占用）、CHANGELOG/commit message 里引用 S-ID 时天然带项目信息。

弊：ID 变长；存量无前缀 S-ID（S-YYYYMMDD-NN）面临迁移决策——不建议回填改写历史 ID（可能已被引用），建议只对切换日期之后的新增条目要求带前缀，旧 ID 按惯例视为"记忆系统"项目遗留格式，在 AGENTS.md 里加一条迁移说明即可。

hook 适配：

S-ID 消失检测：从"对单一 STATE.md 做 diff"改为"对 STATE/*.md 逐文件 glob 检测"，根索引页不参与此项检测（见下方"索引页只读生成"设计）。
已完成 ≤8 条：下沉为每个项目页各自独立的窗口，不做全局计数——这是方案 B 相对方案 A 的关键收益，否则挤占问题（问题1）依然存在。
4. 决策归属

DECISIONS 写频率低、天然 append-only 冲突率低，不需要物理拆分，用强制 scope 标签解决即可：

每条决策必须以 [全局] 或 [项目:课件] 开头，pre-commit 正则校验，缺标签直接拒绝提交。
D-ID 同步带 scope：D-全局-YYYYMMDD-NN / D-课件-YYYYMMDD-NN，与 S-ID 命名逻辑保持一致，便于统一 grep。
SUPERSEDES 只能在同 scope 内生效——项目决策要"覆盖"全局规则时，不要用 SUPERSEDES 声称改变了全局决策，而是新增一条项目 scope 决策并注明"对全局 D-全局-XX 的项目内例外"。
80 条归档阈值：建议先按全局计数跑一段时间（决策量通常远低于状态更新，暂不需要按项目拆分计数），如果某项目决策产出速度明显偏高导致挤占归档窗口，再引入按 scope 的子计数（见"需确认"）。
5. 检索与读取协议

新协议（配合方案 B）：

读根 STATE.md（索引页，≤20 行，一行一个项目：名称/最后更新时间/进行中条数/链接）——建立跨项目的最小全局感知。
读 STATE/<本项目>.md（自己项目的完整状态页，全文）。
跑 scripts/decisions-for.sh <本项目>，读取 [全局] + [项目:本项目] 的决策子集。
CHANGELOG 不再作为会话起手必读项（这本来就是流水日志，不是快照），只在需要排障/追溯时按需跑 scripts/changelog-for.sh <本项目>。

这样每个 agent 实际"读到的一页纸"仍然只包含自己项目 + 全局原则，不被其他项目污染，同时索引页保留了系统级可见性。

推荐方案（可落地）
文件结构
ai-hub-memory/
├── AGENTS.md                    # 协议，全局唯一，不变
├── STATE.md                     # 索引页（新角色）：脚本生成，≤20行，不手改
├── STATE/
│   ├── 记忆系统.md                # ≤60行/≤12KiB，含本项目"进行中"+"已完成≤8条"
│   ├── 课件.md
│   └── 教学.md
├── DECISIONS.md                  # 单文件不拆，每条强制 [全局]/[项目:xx] 标签
├── CHANGELOG.md                  # 单文件不拆，每条强制 [全局]/[项目:xx] 标签
└── scripts/
    ├── regen-index.sh            # 汇总 STATE/*.md 生成根 STATE.md，唯一写入方式
    ├── decisions-for.sh <proj>   # 输出 [全局]+[项目:proj] 决策子集
    └── changelog-for.sh <proj>   # 输出该项目相关流水子集
S-ID / D-ID 命名规则
S-<项目码>-YYYYMMDD-NN，项目码用稳定英文/拼音缩写（如 mem / courseware / teach），避免未来项目改名导致 ID 语义漂移；NN 为该项目当日独立计数器。
切换日期前的历史 S-ID（无前缀）不回填改写，默认归属"记忆系统"项目，AGENTS.md 加一句迁移说明。
D-<scope>-YYYYMMDD-NN，scope 取值为 全局 或项目码；SUPERSEDES 仅限同 scope。
hook 适配
S-ID 消失检测：改为对 STATE/*.md 逐文件 glob 校验；索引页 STATE.md 不参与（它是生成产物）。
已完成 ≤8 条 / ≤60 行 / ≤12KiB：下沉为每个项目页独立的预算，不做全局合计；索引页另设更小上限（≤20 行）。
新增标签校验：CHANGELOG/DECISIONS 每条必须以 [全局] 或 [项目:xx] 开头，正则强制，缺失直接拒绝提交。
新增索引页保护：STATE.md 文件头写自动生成标记，pre-commit 检测该标记是否仍在、且非脚本产生的大段手工 diff 一律拒绝——防止索引页退化成"第二个真源"，重演 routing_group 式双写不一致。
读取协议条文（草案，替换原"新项目单元读 STATE+DECISIONS"）

新项目单元开始时，Agent 依次执行：

读根 STATE.md（全局索引，一页）；
读 STATE/<本项目>.md（本项目完整状态页）；
执行 scripts/decisions-for.sh <本项目> 并阅读输出；
CHANGELOG.md 不作为常规启动读取项，仅按需通过 scripts/changelog-for.sh <本项目> 检索历史。

写入协议不变（git pull --ff-only → 重读本项目 STATE 页 → 改 → commit → push → 完成后如涉及索引信息变化需运行 regen-index.sh 单独提交），单写者语义现在是"每个项目页各自单写者"，而非全仓库单写者。

风险
迁移期新旧 S-ID/D-ID 格式混用，自动化脚本若正则写得不够宽容会漏判归属。
索引页若缺少强制的"脚本生成"校验，会逐渐被手改污染，重演双写不一致问题。
项目码一旦固化进 ID，未来项目改名/合并/拆分会与新名字脱节，需要预留别名映射空间。
标签依赖人工自觉，若 hook 校验不到位会逐渐腐化失效，导致过滤脚本结果不准。
项目数很少（1-2个）时上方案 B 的索引+脚本反而增加认知负担，收益低于成本。
DECISIONS 全局 80 条归档阈值下，若某项目决策产出频率远高于其他项目，会让归档窗口被高频项目主导。
需确认
三个项目的英文/拼音项目码具体定什么（如 mem / courseware / teach），需要你拍板，要选不易与未来新项目冲突的短码。
存量无前缀 S-ID 是否需要在 CHANGELOG 里补一条一次性迁移说明，还是完全不动、仅对切换日期后生效？
DECISIONS 的 80 条归档阈值，先按全局计数跑一段时间观察，还是现在就拆成全局池/项目池分别计数？
索引页 STATE.md 的更新方式：项目页改完后由 agent 显式手动跑 regen-index.sh 再单独提交（更符合"极简+显式"精神），还是让 pre-commit hook 自动触发重生成并一并提交（更省一步但会让"改了自己项目却看到索引连带变化"变得不那么直观）？
方案 C（完全目录化）的触发阈值——项目数到 5 还是 6 个时该复审升级？现在先在 AGENTS.md 里挂一条"未来复审条件"占位，还是先不定、到时候再议？
