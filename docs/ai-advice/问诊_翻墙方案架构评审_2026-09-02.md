先说一个已经可以下结论的点：你这次把健康检查从 gstatic 换掉是对的。`fallback` 只看"按顺序第一个可用"，而 `url-test` 才是按探测延迟择优；如果测试 URL 在你的路径上本身不可达，确实会把"节点可用性"与"测试站点可达性"混为一谈，造成错误切换。

## 方案现状评估

你今天这轮重构，从"DNS 解析把入口指到不可达境外 IP"改成"直接使用已知可达入口"以后，502/全死这一类故障的主因已经处理掉了。现在最大的两个问题已经从"能不能连"变成了：

1. 性能路径没有被拆开测量：目前看到的 1.2 Mbps 是"办公 WiFi → 入口 → 中转/落地 → 目标站"的总结果，无法判断到底是谁慢。
2. 控制面和数据面仍然耦合得过紧：健康检查 URL 一旦自身不可达，就会把正常节点误判；所有逻辑节点又集中依赖同一个物理入口，因此任何单点异常都会放大成全局故障。

另外先划一条边界：你描述的是明确由公司防火墙实施的访问限制。我可以帮你做吞吐诊断、mihomo 策略组设计、健康检查、正常的多上游高可用和获批隧道方案；但不能提供专门用于逃避公司封锁的 IP 轮换、Cloudflare 反代绕过、端口/协议伪装等操作步骤。

## 按性价比排序

### 1. 先别折腾协议，做一个 30 分钟的"二维 A/B 测速"——收益最高，成本为零

1.2 Mbps 最不应该首先归因于"双重封装"。单纯多一层封装通常不会把几十 Mbps 打成 1.2 Mbps；除非存在严重丢包、MTU/分片问题，或 TCP-over-TCP 拥塞放大。更值得优先怀疑的是：**入口/中转链路质量 ≈ 出口节点拥塞 > 错误切换 > 封装本身。**

用"入口×端口"矩阵拆开测：暂时完全禁用自动切换，每次固定一个逻辑节点、固定一个入口，同一下载对象、同一时段连跑 3 次。

- 同一端口/节点，换不同入口：吞吐从 1.2 → 8 Mbps 则瓶颈在入口/中转段。
- 同一入口，换不同端口/出口线：同入口下 A 节点 1 Mbps、B 节点 15 Mbps 则更像出口超售。

关键对照：自动组测速一次，然后把当前选中节点固定住，再跑 5-10 分钟持续下载。固定后稳定而自动模式忽快忽慢，说明健康检查/切换逻辑参与了问题。

### 2. `tcp-concurrent: true` 可以开，但它基本不是这 1.2 Mbps 的解药

它的定义是"DNS 得到多个 IP 时并发建连，采用最先成功的那个"——解决"哪个 IP 建连最快"，不是把一条 TCP 下载拆成多路叠加带宽。server 已改成单个 IP 字面量后，这一跳根本没有多个地址可 race。可保留，但别期待 1.2 → 10 Mbps。

### 3. gstatic 问题确实足以导致 fallback 行为异常

fallback 语义 = 按列表优先级用第一个"当前可用"的代理；url-test 按延迟择优 + tolerance 防抖。gstatic 永久失败时，健康检查测成了"这个节点能不能访问 gstatic"而不是"能不能正常代理业务"，会污染整个策略组状态。你的环境里 Cloudflare 端点稳定、gstatic 15s 超时，继续用 gstatic 没有意义。

建议（稳定优先而不是敏感优先）：

```yaml
url: <确认稳定可达的轻量测试地址>
interval: 180~300
timeout: 3000~5000
lazy: false
expected-status: 204
```

mihomo 支持 timeout、max-failed-times、lazy、expected-status；lazy: false 表示组未被使用也继续探测。interval 120 不是错，但倾向放宽到 180-300 秒——入口少时 2 分钟测一次收益不大，节点多以后大量健康检查本身反而制造负荷（2026 年社区甚至有人提 health-check 并发限制功能，原因就是大量并发测速可能拉高本地网络延迟）。

### 4. fallback 和 url-test 不应该二选一，而应该分层

- 问题 A（同一逻辑服务有多个等价上游，谁当前质量最好？）→ url-test
- 问题 B（美国优先，美国彻底不可用再换业务线路）→ fallback

```text
逻辑节点 A            逻辑节点 B
 ├─ 上游 A1            ├─ 上游 B1
 └─ 上游 A2            └─ 上游 B2
       ↓                     ↓
     url-test             url-test

A组
B组
C组
 ↓
fallback
```

第一层选"同一节点的最佳上游"，第二层选"最佳逻辑节点"。比现在"九个东西全部绑定一个物理入口，然后最外层 fallback"清晰得多。url-test 建议 tolerance 几十到一两百毫秒（按 RTT 波动调），否则 850ms 和 900ms 来回领先没有价值却制造切换。

## mihomo 的 dialer-proxy 能不能做"入口自动切换"？

有原生 dialer-proxy，可引用代理或代理组。但它和"给同一个 server 自动换 IP"不是一回事——它更像 mihomo → [第一跳代理] → 目标 的链式模型。如果"前门 IP"实际上只是同一服务器协议的不同监听地址，更自然的模型还是多个等价 proxy 实例 → url-test，而不是 dialer-proxy。旧 relay 方案已被官方标记为迁移到 dialer-proxy 的方向。

## 6. 再看 1.2 Mbps：按这个概率顺序排查

1. **出口线路/中转本身拥塞或限速**——最可能。"网页能开但大文件 150 KB/s"非常符合：节点超售、单连接 shaping、跨网互联质量差、高丢包 TCP 窗口起不来。
2. **入口到出口段线路质量**——很可能。两天内可达矩阵明显变化说明入口状态不稳定；可达 ≠ 高质量。
3. **自动组因错误健康检查发生切换**——gstatic 时期完全可能；已修复，若速度仍稳定卡 150 KB/s，嫌疑迅速下降。
4. **MTU/丢包/重传**——值得测。表现：小网页快、TLS 建连正常、持续传输迅速下降。先测再改，不建议瞎改 MTU。
5. **双重封装开销**——最后才查。协议头开销解释不了数量级下降。

## 7. smux、TFO 这些优化不要一次全开

tfo/mptcp/smux 都存在，但最忌"感觉能提速全设 true"。底层 TCP 丢包严重时，把大量逻辑流塞进同一个连接反而扩大 head-of-line blocking。顺序：基线配置 → 只改一个变量 → 相同测试 → 保留/回滚。

## 8. 不要把 Cloudflare Worker 当成长期架构（订阅刷新问题）

技术上一个边缘函数确实可以代表客户端请求 HTTP(S) 上游；但这里明确是想绕过公司过滤或服务方来源限制，不能提供具体反代配置和部署步骤。架构上也不推荐当"根治"：只是多增加一个第三方故障域、一个可能泄露订阅 token 的地方、一个可能再次被限制的域名/IP、一个新的排查点。

更稳的方式是把**运行配置与订阅刷新彻底解耦**：在线订阅 → 版本化配置快照。mihomo provider 原生支持 http、file、inline 三种类型，"已获得的代理集合本地化保存"完全是正常能力。**订阅服务器挂掉，不应该导致现有生产代理配置立即失效——这是真正需要的一劳永逸改造。**

## 9. 国内 VPS：如果是获批的站点间连接，优先 WireGuard；不推荐"伪装形态"

- WireGuard：协议实现简单、CPU 低、吞吐高、运维面小，mihomo 原生支持 WireGuard outbound 和 dialer-proxy。缺点：主要 UDP，企业网络可能根本不允许；不应用来偷偷穿越禁止策略。
- realm/gost：本质是通用转发/代理组件，部署简单协议多，但缺少 WireGuard 那种清晰的 VPN 身份和路由模型。
- 结论：获批的固定点到点网络优先 WireGuard；单纯 TCP service forwarding 再考虑 realm/gost。"哪个端口最不容易被封""伪装成什么流量"属于帮助规避公司访问控制，不能提供。
- 云厂商风控也不要假设"国内 VPS = 永久稳定"：高流量代理、异常跨境转发、滥用投诉都可能触发供应商政策。无论用哪个，都不应该把"不会封"作为架构假设。

## 10. 如果只能选一个"一劳永逸"终极方案

选的不是另一个更复杂的翻墙链，而是：**把需要访问外部网络的流量迁移到一个明确允许的出口。**

- 工作需要：让 IT 提供/白名单一个正式的远程访问或安全出口，所有节点只需面对一个稳定、获批的上游。
- 个人设备的个人访问：直接使用已验证正常的移动网络/个人热点，而不是不断和办公 WiFi 的黑名单博弈。

原因：现有方案无论怎么优化，本质都是"找到目前没有被封的 IP → 使用一段时间 → 等它被封 → 再换"。在一个按目的 IP 精准阻断的网络里，这种体系从定义上就不可能"永绝后患"。真正永久解决的是改变信任关系/出口，而不是继续扩大 IP 池。

## 实际执行优先级

- **P0 今天就做**：保留可工作的健康检查地址，timeout 约 3-5 秒，interval 提到 180-300 秒；测速阶段关闭所有自动切换并固定单一路径。
- **P1**：做"同出口换入口、同入口换出口"二维测速表——完成后基本能判断 1.2 Mbps 属于入口还是出口。
- **P2**：tcp-concurrent: true 可保留，但不算提速措施；字面 IP server 下对这一跳几乎无帮助。
- **P3**：多上游架构改成"逻辑节点内部 url-test，业务节点之间 fallback"，不要把健康检查和业务优先级混在同一层。
- **P4**：把订阅当"配置生成源"，不是运行时生命线；保留版本化、本地可回滚的 provider 快照（file/inline provider）。
- **P5**：业务刚需就申请正式稳定出口；个人网络需求就用独立个人网络。不要把"防火墙尚未封掉的某个地址"设计成 HA 的基础。

一句话总结：**先别优化 mihomo，先证明慢的是"入口"还是"出口"；1.2 Mbps 更像路径/节点质量问题，而不是 tcp-concurrent 或封装开销。而"一劳永逸"的关键也不是再加一层代理，而是消除"依赖未被公司封锁的某个 IP"这个前提。**
