二、五个问题的直接回答

1. 提示词注入是否足够

不够做“可靠保证”，适合作为所有 Agent 的最低兼容层。你自己的 AGENTS.md 已明确写着：“本文件是『启动引导』，不是『强制配置』”；而方案也承认 LLM 数轮次不可靠。更关键的是，目前 memory.py read 实际只输出指定 STATE/DECISIONS 文件，并不会把 RULES 一并返回，所以“读项目记忆即注入 R18”目前并未机械成立。建议把“10轮”降级为 watchdog，主触发改为“可交付完成/决策拍板/关键状态变化/交接”。

2. 机制强制层怎么落地

DSH 插件合理，最佳落点是一个完整 user→agent turn 已提交之后、loop 返回 idle 之前，不要按 tool call/token 计数。Claude Code 则不是“hooks 或 MCP”二选一：hook 管什么时候触发，memory.py/MCP 管怎样保存。周期计数用 UserPromptSubmit，任务边界可用 TaskCompleted，到期用 Stop 注入 checkpoint 并让 Claude 继续一次；PreToolUse 更适合守卫写操作，不适合计轮。

3. 防污染设计是否够

4. 与 R14 的边界

你的理解基本正确。R14 原文主语就是 “Consolidation 采用 Lazy Daily Consolidation”，禁止的是给 consolidation 搭 cron / Actions schedule / daemon；同一 RULES 后面又明确规定“可交付单元完成 → memory.py write”。所以会话内、由 Agent 生命周期事件触发的 checkpoint/save 不违反 R14。但应避免把“每10轮”实现成独立常驻 scheduler；必须明确它只是 agent-loop 内事件。

5. 新项目场景

已有项目可以先由 MEMORY.json 唯一路由，再注入 RULES+STATE；当前表里例如 memory-system、devel-tools 都已有 aliases/path。新项目注册前则绝不能因为内容“看起来像某项目”直接正式写入：memory-router 现有流程也是“无匹配→只读 global→后续 register”，R1'/R7 又允许 UNKNOWN capture。因此最稳的是：注册前 capture，用户/确定性证据确认后 register+promote；从注册成功后的下一次 bootstrap 起进入正常自动 checkpoint。

三、推荐落地方案
1. 先改 global/RULES.md

你现在标题仍叫“16 条宪法”，但文件实际上已经存在 R17；因此加 R18 时建议顺便把标题改成“18 条宪法”或干脆改成不带数量的“全局宪法”，否则版本号会继续漂移。

R18 建议不要写成纯“10轮自动保存”，而写成：

**R18 自动记忆检查（Memory Checkpoint）：**出现以下任一事件时主动检查是否产生值得跨会话保留的信息：可交付单元完成、用户拍板决策、关键共享状态变化、Agent/会话交接；若连续约 10 个用户回合均未发生检查，则强制执行一次兜底检查。检查不等于写入：符合 R13 才写正式记忆；项目明确则 write，项目未定则 capture；无新增价值则跳过。可控的会话结束/交接前必须执行 checkpoint。异常中断以最近一次成功 checkpoint 为恢复点。

这里最重要的改变是：

事件触发优先 + 10 回合 watchdog，而不是 10 回合本身作为业务语义。

“轮”也应定义成 一个 user prompt = 一个用户回合，这样 DSH/Claude Code 都能机械计数，不让 LLM 自己数。

2. 改 AGENTS.md 和 memory-router/SKILL.md

不要复制完整 R18，保持 RULES 单一真源，只加一句引用：

进入任何项目记忆线时必须加载 RULES 中的 Memory Checkpoint 规则；后续按 R18 执行。禁止依赖模型自行记住轮次，平台存在 lifecycle hook 时由 hook 提供 checkpoint_due 信号。

这符合你方案中“RULES 单一真源、AGENTS/SKILL 同步引用”的原设计。

3. 最值得先改的是 memory.py：增加统一 bootstrap

目前 cmd_read() 实际是找到目标文件后直接 print(f.read_text(...))，所以仅仅执行 memory.py read --project X --file state 并不会注入 R18。

我建议不要偷偷改变 read 的语义，而新增：

Bash
python scripts/memory.py bootstrap --project <id> [--capture-scope <scope>]

固定返回：

1. global/RULES.md 中 Agent 必须遵守的规则/Checkpoint policy
2. projects/<id>/STATE.md
3. projects/<id>/DECISIONS.md
4. 当前项目可见 staging
5. 明确的：
   MEMORY_PROJECT_ID=<id>
   MEMORY_CHECKPOINT_POLICY=R18

以后所有 Agent 的标准入口变成：

bootstrap，而不是分别 read STATE / RULES。

这样才真正满足你的目标：Agent 只要进入这条记忆线，就同时拿到项目上下文和自动保存规则。

纯网页 Agent 无法运行这个命令时，仍退化到 AGENTS/RULES 提示词层。

4. 再补一个 GitHub 真源缺口

这是我实读 memory.py 后认为必须改的地方：

当前 cmd_write() 会先 git pull --ff-only，再修改 STATE/DECISIONS/CHANGELOG；代码里没有 commit，也没有 push。因此：

Bash
memory.py write

目前严格说只是“本地保存”，还不是“多 Agent 共享记忆真源保存”。

建议新增一个事务入口，例如：

Bash
python scripts/memory.py checkpoint \
  --project memory-system \
  --kind state \
  --sid S-20260815-XX \
  --content "..." \

内部统一：

→ git pull/fetch 最新
→ 重读 STATE
→ 幂等检查 checkpoint-id
→ write_memory_entry
→ validate
→ git add 指定记忆文件
→ commit
→ push

push 被远端抢先时，不得拿旧 STATE 重试，必须重新获取最新版本并重新应用这次逻辑更新。

你的 R16 secret preflight 已经在 capture 路径真实存在，这部分方向很好。

5. DSH agent-loop

我会采用下面这个状态机，而不是简单 if turn % 10 == 0: write()：

turn_committed
    ↓
user_turns_since_checkpoint += 1

如果：
  deliverable_completed
  OR decision_committed
  OR shared_state_changed
  OR handoff_requested
  OR user_turns_since_checkpoint >= 10
    ↓
MEMORY_CHECKPOINT_DUE
    ↓
Agent 判断：
  durable + project明确 → checkpoint/write
  durable + project不明 → capture
  无价值 → SKIP(reason)
    ↓
记录 checkpoint 已完成
user_turns_since_checkpoint = 0

最佳 hook 点：

onTurnCommitted()       // 主 watchdog
onDeliverableComplete() // 语义触发
onDecisionCommitted()   // 语义触发
onBeforeHandoff()       // 强触发

不要挂在：

onToolCall()
onToken()
onLLMChunk()

否则工具密集型任务会“十几秒保存一次”，对话型任务又可能很久不保存。

checkpoint 状态放 DSH session metadata 或本地未跟踪 sidecar，不要写进 STATE。

四、风险

**规则注入假象：**只把 R18 写进 RULES 而不改 bootstrap，无法保证“读 STATE 就看到 R18”。

**本地写≠共享保存：**现有 memory.py write 不 commit/push，自动 checkpoint 必须把 Git 落地闭环补上。
+1

**并发竞态：**R5 的 single-write-scope 不等于跨进程单写者，现有代码也未发现锁机制。
+1

**重复 checkpoint：**Stop/TaskCompleted/watchdog 可能同时命中，必须用 checkpoint_id 幂等。

**STATE 膨胀：**周期 checkpoint 只能记录“当前仍有用的状态”，否则会迅速撞上现有 ≤60 行、≤12 KiB 约束。

**异常退出：**Claude Code 的 Stop 不会在用户 interrupt 时触发，所以“任何退出都保证最终交接”不能只靠 Stop 实现。
Claude Platform Docs

**SessionEnd 能力有限：**它不能阻止退出，默认超时也很短，因此只能做最后的机械 side-effect，不应在此临时要求 LLM 生成复杂摘要。
Claude Platform Docs

**规则编号漂移：**RULES 目前标题仍写“16 条宪法”却已有 R17，加 R18 时应同步修正标题和 memory.py 中仍写着 R1'-R16 的说明。
+1

**新项目误归属：**注册前自动正式写入会破坏 Routing-before-Retrieval / Fail Closed，应保持 UNKNOWN capture 隔离。

五、需用户拍板的点

我认为只需拍板三个架构选择：第一，R18 是否正式定义为“事件优先 + 10 用户回合 watchdog”，而不是“固定每10轮写一次”；第二，是否把 memory.py bootstrap 定为所有 Agent 唯一的项目记忆入口，从根上解决注入问题；第三，是否把 Git commit/push 纳入新的 memory.py checkpoint 原子流程。

这三项我都建议选“是”。其中 bootstrap + checkpoint 两个命令 是我认为最关键的改动；做好之后，DSH/Claude Code/未来 MCP 都只是不同适配器，真正的记忆规则与事务语义仍然只存在于 ai-hub-memory 这一份真源中。
