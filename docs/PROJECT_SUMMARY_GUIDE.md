# 项目说明编写指南

> 本文档指导如何为 Feishu Data Hub 的每个项目编写 `summary.md`——面向 AI 代理的项目业务说明文件。

---

## 1. summary.md 的目的

### 1.1 定位

`summary.md` 是项目的**业务语义摘要**，回答"这个项目是什么、有什么数据、数据之间什么关系、AI 应该怎么理解这些数据"。

它与以下文件互补但不同：

| 文件 | 回答的问题 | 维护方式 |
|---|---|---|
| `manifest.json` | 有哪些表、各表多少条记录、校验和是什么 | 代码自动生成 |
| `schema.json` | 有哪些字段、字段什么类型、表之间什么关联 | 代码自动生成 |
| `semantic.json` | 字段在业务上是什么含义、表扮演什么角色 | 代码从 YAML 构建 |
| `agent-guide.md` | AI 应该怎么分析、什么不能做 | 人工维护 |
| **`summary.md`** | **这个项目是做什么的、数据怎么用、有什么限制** | **人工维护** |

### 1.2 为什么需要人工编写

在语义层引入之前，`summary.md` 由 `sync-project.mjs` 的 `buildProjectSummary()` 函数自动生成，内容是表清单和字段列表的机械汇总。这种机械汇总无法回答：

- 项目的业务目的是什么？
- 表与表之间在业务上是什么关系？
- 哪些状态字段和指标是分析的关键？
- 常见的分析问题应该怎么回答？
- 数据有什么已知限制？
- AI 不应做出哪些推断？

这些问题需要理解业务上下文的人工编写者来回答，代码无法自动生成。

### 1.3 面向的读者

`summary.md` 的主要读者是 **AI 代理**。AI 代理在分析项目数据前会先读取 `summary.md` 来建立业务上下文。因此，编写风格应：

- 直接、明确，避免含糊表述
- 使用项目实际的表名和字段名（中文原名）
- 提供可操作的分析路径，而非泛泛的描述
- 明确标注限制和禁忌，防止 AI 做出错误推断

## 2. 必须包含的章节

`validate-ai-docs.mjs` 校验 `summary.md` 必须包含以下 10 个章节标题。缺少任何一个都会导致校验失败。

### 2.1 章节清单

| 序号 | 章节标题 | 校验关键字 |
|---|---|---|
| 1 | 项目用途 | `项目用途` |
| 2 | 核心目标 | `核心目标` |
| 3 | 主要数据表 | `主要数据表` |
| 4 | 表之间的关系 | `表之间的关系` |
| 5 | 关键状态和指标 | `关键状态和指标` |
| 6 | 常见分析问题 | `常见分析问题` |
| 7 | 推荐读取顺序 | `推荐读取顺序` |
| 8 | 数据更新时间与时效性 | `数据更新时间与时效性` |
| 9 | 数据公开范围 | `数据公开范围` |
| 10 | 已知限制 | `已知限制` |
| 11 | 不应做出的推断 | `不应做出的推断` |

> 注：`关键状态和指标` 虽然不在 `validate-ai-docs.mjs` 的必需章节列表中（该校验脚本检查 10 个章节），但它是完整项目说明的重要组成部分，应在编写时包含。校验脚本检查的 10 个章节为：`项目用途`、`核心目标`、`主要数据表`、`表之间的关系`、`常见分析问题`、`推荐读取顺序`、`数据更新时间与时效性`、`数据公开范围`、`已知限制`、`不应做出的推断`。

### 2.2 各章节编写要求

#### 项目用途

**内容：** 用 2-3 段话说明项目是什么、解决什么问题、核心使用者是谁。

**编写要点：**
- 说明数据来源（飞书多维表格公开导出）
- 说明项目的业务领域（英语学习、公考备考等）
- 说明核心使用者（AI 代理、学习者本人）
- 说明数据形态（静态 JSON、每小时同步、GitHub Pages 部署）

**示例（learning-english）：**
> 本项目是一个个人英语学习的完整数据系统，从飞书多维表格公开导出，供 AI 工具和其他消费者读取数据模型、记录和表间关联，无需飞书访问权限。系统覆盖英语学习的完整闭环：词汇积累、文本阅读、计划制定、学习执行、测验记录、能力追踪和错误改进。

#### 核心目标

**内容：** 用编号列表列出项目的 5-7 个核心目标。

**编写要点：**
- 每个目标对应一张或多张核心表
- 目标应是具体的、可度量的业务目标，而非技术目标
- 与项目的 capabilities 对应

**示例（civil-service-exam）：**
> 1. **目标导向**：以 `target-positions` 中的目标岗位为锚点，把竞争比、历年分数线转化为复习优先级。
> 2. **知识可追踪**：以 `knowledge-points` 为知识主干，记录每个知识点的掌握状态和复习节奏。

#### 主要数据表

**内容：** 用表格列出所有表，然后用分节列出每张表的字段。

**编写要点：**
- 表格列：序号、飞书表名、slug、记录数、字段数、用途
- 记录数和字段数必须来自 `manifest.json`，不能虚构
- 用途说明应简明扼要，一句话说清这张表是做什么的
- 字段列表直接列出字段名，用顿号分隔

**示例格式：**
```markdown
| # | 飞书表名 | Slug | 记录数 | 字段数 | 用途 |
|---|---|---|---|---|---|
| 1 | 文本库 | `text-library` | 30 | 18 | 阅读文本管理 |
```

#### 表之间的关系

**内容：** 用图表或表格列出表间关联关系，并说明关系的业务含义。

**编写要点：**
- 关系必须来自 `schema.json` 中的关联字段（`relation`），不能虚构
- 区分"显式关联"（有外键字段）和"隐含语义关联"（需通过字段值匹配）
- 明确标注哪些表之间**没有**显式关联，防止 AI 假设关联
- 用 ASCII 图表或表格清晰展示关系拓扑

**示例（learning-english）：**
```
vocabulary.关联文本 ────────────→ text-library
vocabulary.学习日志 ────────────→ learning-log
learning-log.关联单词 ──────────→ vocabulary
daily-plan.单词列表(link) ──────→ vocabulary
```

#### 关键状态和指标

**内容：** 按表分组，列出关键的状态字段和指标字段，说明其用途。

**编写要点：**
- 状态字段：掌握状态、记忆阶段、完成状态等
- 指标字段：正确次数、学习次数、正确率、连续成功/失败次数等
- 说明 AI 应如何使用这些字段做判断
- 标注哪些字段是间隔重复系统的核心（如 `下次复习`、`记忆阶段`）

#### 常见分析问题

**内容：** 列出 5-7 个该项目的常见分析问题，每个问题给出数据来源和判断方法。

**编写要点：**
- 每个问题包含：问题描述、数据来源（表名）、判断方法（筛选条件/排序逻辑）、注意事项
- 问题应覆盖项目的主要使用场景
- 注意事项中标注样本量限制、时区假设、空值处理等
- "今天"的定义应基于 `generated_at` 而非 AI 系统时钟

**示例格式：**
```markdown
### 1. 哪些词需要复习？

**数据来源：** `vocabulary` 表

**判断方法：**
- 筛选 `下次复习` 字段 <= 当前日期的记录
- 结合 `掌握状态` 和 `记忆阶段` 判断紧迫程度

**注意：** 当前日期应以数据的 `generated_at` 为基准。
```

#### 推荐读取顺序

**内容：** 用表格列出 AI 代理分析本项目时的推荐读取顺序。

**编写要点：**
- 按步骤编号，每步包含文件/表名和目的
- 原则：先读元数据（manifest/schema/status），再读核心数据，最后读辅助数据
- 说明根据具体问题可以跳过哪些表
- 与 `agent-guide.md` 的"读取顺序"章节保持一致

**示例格式：**
```markdown
| 步骤 | 文件/表 | 目的 |
|---|---|---|
| 1 | `manifest.json` | 了解项目结构 |
| 2 | `schema.json` | 了解数据模型 |
| 3 | `status.json` | 确认数据新鲜度 |
| 4 | `vocabulary` | 核心数据：筛选到期复习词 |
```

#### 数据更新时间与时效性

**内容：** 说明同步频率、如何判断数据新鲜度、时效性注意事项。

**编写要点：**
- 说明同步层级（hourly/daily）和触发时间
- 说明如何从 `status.json` 判断 stale
- 说明如何从 `manifest.json` 获取 `generated_at`
- 强调数据是快照而非实时流
- 说明日期字段的时区可能

#### 数据公开范围

**内容：** 说明导出范围的控制机制和公开约束。

**编写要点：**
- 三层防护：视图级（`AI 公开导出` 视图）、字段级（显式白名单）、内容级（安全扫描）
- 说明 `require_public_flag` 的设置及含义
- 列出不公开的数据类型（凭据、内部标识符、PII）
- 说明 `mirror_to_legacy_root` 的设置

#### 已知限制

**内容：** 列出数据规模限制、结构限制、时效性限制和内容限制。

**编写要点：**
- 数据规模限制：标注记录数极少的表（如 < 10 条），说明其统计意义不足
- 结构限制：标注缺少显式关联的表对
- 时效性限制：强调数据是快照，非实时
- 内容限制：标注字段值域不统一、自由文本质量不均等问题

**示例：**
```markdown
| 表 | 记录数 | 限制说明 |
|---|---|---|
| `study-sessions` | 3 | 记录极少，无法进行趋势分析 |
| `error-remediation` | 8 | 样本量小，错误模式分析可能不具统计意义 |
```

#### 不应做出的推断

**内容：** 用编号列表列出 AI 不应做出的推断。

**编写要点：**
- 每条推断用"不应..."开头，明确禁止
- 每条附上理由和应使用的正确判断方法
- 与 `agent-guide.md` 的"禁止推断"章节保持一致
- 覆盖常见误区：看过=掌握、单次正确=长期掌握、稀疏数据=趋势、内部等级=外部标准等

**示例：**
```markdown
1. **不应将"看过"等同于"掌握"**：`学习次数` 高不代表掌握状态好，必须参考 `掌握状态`、`记忆阶段` 和 `正确次数`。
2. **不应从稀疏数据推断趋势**：`study-sessions`（3 条）样本量太小，不应据此做出趋势性结论。
```

## 3. 编写原则

### 3.1 基于真实 schema 和 manifest，不虚构

这是最重要的原则。`summary.md` 中的所有表名、字段名、记录数、字段数、关联关系必须来自真实的 `schema.json` 和 `manifest.json`，不能虚构。

**具体要求：**
- 表名和 slug 来自项目配置 `config/projects/<slug>.yaml`
- 字段名来自 schema.json 的 `fields` 数组
- 记录数和字段数来自 manifest.json
- 关联关系来自 schema.json 的 `relation` 字段
- 选项值（如 `掌握状态` 的可选取值）来自 schema.json 的 `options`

**验证方法：** 编写完成后，对照 `public/projects/<slug>/schema.json` 逐一核对所有引用的表名和字段名。

### 3.2 使用项目术语

- 使用飞书表名和字段名的**中文原名**（如"掌握状态"、"下次复习"）
- 引用 slug 时使用反引号（如 `vocabulary`、`study-tasks`）
- 不自行翻译或改写字段名
- 不用同义词替代（如不用"复习日期"替代"下次复习"）

### 3.3 标注不确定性

- 对样本量不足的分析，标注"样本量小，结论为定性参考"
- 对时区不确定的字段，标注"可能使用 UTC+8 或 UTC"
- 对未确认的关联，明确标注"无显式关联字段，不应假设关联"
- 对状态字段的取值，说明"具体可选取值以 fields.json 的 options 为准"

### 3.4 区分事实和建议

- "事实"是数据中直接可见的信息（如"该表有 6000 条记录"）
- "建议"是基于数据的分析推断（如"建议优先复习到期的词"）
- `summary.md` 以陈述事实为主，建议性内容放在 `agent-guide.md`

### 3.5 保持与 agent-guide.md 一致

`summary.md` 和 `agent-guide.md` 是互补文件，两者在以下方面必须保持一致：
- 推荐读取顺序
- 已知限制
- 不应做出的推断
- 关键状态字段和指标字段

如果更新了其中一个文件的这些内容，必须同步更新另一个。

## 4. 源文件位置

### 4.1 源文件

```
content/projects/<slug>/summary.md
```

**当前项目的源文件：**
- `content/projects/learning-english/summary.md`
- `content/projects/civil-service-exam/summary.md`

### 4.2 构建时复制到公开目录

`summary.md` 在 `sync-project.mjs` 同步过程中被原样复制到公开目录：

```
content/projects/<slug>/summary.md
    │
    │  sync-project.mjs
    │  ├── fs.readFile(summarySourcePath)
    │  ├── assertNoSecrets(content, secretValues)   ← 安全扫描
    │  └── fs.writeFile(tempDir/summary.md, content)
    │
    ▼
public/projects/<slug>/summary.md
```

**关键行为：**
- **原样复制**：代码不修改文件内容，不重新格式化，不添加或删除任何字符
- **安全扫描**：复制前执行 `assertNoSecrets()`，检测到敏感信息则中止同步
- **必须存在**：如果源文件不存在，同步抛出错误中止：`"content/projects/<slug>/summary.md 不存在 — 必须提供人工维护的项目说明"`
- **原子替换**：先写入临时目录（`tempDir`），同步成功后原子替换公开目录

### 4.3 内容长度要求

`validate-semantic.mjs` 和 `validate-ai-docs.mjs` 校验 `summary.md` 的内容长度：
- `validate-semantic.mjs`：内容 >= 500 字符
- `validate-ai-docs.mjs`：内容 >= 500 字符

内容过短会导致校验失败，确保项目说明足够详细。

## 5. 维护规则

### 5.1 不自动覆盖人工内容

**核心规则：** 构建过程不会自动修改 `content/projects/<slug>/summary.md` 的内容。

- `sync-project.mjs` 只执行"读取源文件 → 安全扫描 → 写入公开目录"的复制操作
- 不存在任何代码逻辑会反向修改源文件
- 之前的自动生成函数 `buildProjectSummary()` 仍保留在代码中，但不再被调用（人工文件优先）

### 5.2 何时需要更新

| 变化场景 | 是否需要更新 summary.md |
|---|---|
| 飞书表新增字段 | 是（更新字段列表） |
| 飞书表删除字段 | 是（更新字段列表和关系说明） |
| 飞书表新增/删除 | 是（更新表清单） |
| 记录数显著变化 | 否（记录数在 manifest.json 中，summary.md 可引用近似值或动态说明） |
| 新增关联字段 | 是（更新表之间的关系） |
| 调整语义配置 | 否（语义映射在 semantic.json 中） |
| 调整路由配置 | 否（路由在 routing.json 中） |
| 发现新的限制或禁忌 | 是（更新已知限制和不应做出的推断） |

### 5.3 更新后的验证

修改 `content/projects/<slug>/summary.md` 后，运行：

```bash
# 1. 重新同步（将更新复制到公开目录）
node scripts/sync-project.mjs <slug>

# 2. 语义校验（检查 summary.md 内容长度和章节）
node scripts/validate-semantic.mjs

# 3. AI 文档校验（检查必需章节和安全性）
node scripts/validate-ai-docs.mjs

# 4. 安全扫描（确保无敏感信息）
node scripts/security-scan.mjs
```

### 5.4 与 agent-guide.md 的同步维护

如果 `summary.md` 中的以下内容发生变化，必须检查 `agent-guide.md` 是否需要同步更新：

- 推荐读取顺序
- 已知限制
- 不应做出的推断
- 关键状态字段

两个文件在这些方面的表述应保持一致，避免 AI 接收到矛盾的指引。

### 5.5 模板参考

项目提供了示例模板 `templates/summary.example.md`，可作为新项目编写 `summary.md` 的起点。但模板只是结构参考，所有具体内容必须基于新项目的真实 schema 和 manifest 编写。

## 6. 校验机制

### 6.1 validate-semantic.mjs 中的校验

```javascript
// 检查 summary.md 存在且内容充分
const summaryPath = path.join(projectDir, "summary.md");
const content = await fs.readFile(summaryPath, "utf8");
if (content.trim().length < 500) {
  console.error(`  ✗ summary.md 内容过短（<500 字符）`);
  totalErrors++;
}
```

### 6.2 validate-ai-docs.mjs 中的校验

```javascript
// 检查 summary.md 存在、内容充分、安全扫描通过
// 检查必需章节
const requiredSections = [
  "项目用途", "核心目标", "主要数据表", "表之间的关系",
  "常见分析问题", "推荐读取顺序", "数据更新时间与时效性",
  "数据公开范围", "已知限制", "不应做出的推断"
];
for (const section of requiredSections) {
  if (!summary.includes(section)) {
    console.error(`  ✗ summary.md 缺少章节：${section}`);
    errors++;
  }
}
```

校验逻辑是简单的字符串包含检查（`summary.includes(section)`），因此章节标题必须与上述关键字完全匹配。建议使用 `## ` 二级标题格式编写章节，如 `## 项目用途`、`## 核心目标` 等。
