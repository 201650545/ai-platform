一句话结论

选 “项目作用域隔离的分层记忆模型（Scoped Hierarchical Memory）”：以项目命名空间作为硬隔离边界，以“工作记忆 → STATE 热记忆 → DECISIONS 温记忆 → CHANGELOG/Archive 冷记忆”做分层；不要按 Agent 分记忆，也不要把递归结构作为主存储模型。

1. 记忆线的数据结构

你现有的 STATE.md + DECISIONS.md + CHANGELOG.md + S-ID 不用推翻。真正缺的不是新的记忆格式，而是外面这一层：

Project Namespace + Router

建议最终目录直接定成：

ai-hub-memory/
│
├─ MEMORY.json                 # 唯一“记忆路由表”
│
├─ global/
│  ├─ RULES.md                 # 所有 Agent 必须知道的规则
│  └─ DECISIONS.md             # 真正跨项目的系统级决策
│
├─ projects/
│  ├─ teaching/
│  │  ├─ STATE.md
│  │  ├─ DECISIONS.md
│  │  ├─ CHANGELOG.md
│  │  ├─ INDEX.json            # 脚本生成，不手写
│  │  └─ archive/
│  │
│  ├─ slides/
│  │  ├─ STATE.md
│  │  ├─ DECISIONS.md
│  │  ├─ CHANGELOG.md
│  │  ├─ INDEX.json
│  │  └─ archive/
│  │
│  └─ memory-system/
│     ├─ STATE.md
│     ├─ DECISIONS.md
│     ├─ CHANGELOG.md
│     ├─ INDEX.json
│     └─ archive/
│
├─ scripts/
│  └─ memory.py                # 唯一正式读写入口
│
├─ skills/
│  └─ memory-router/
│     └─ SKILL.md
│
└─ .githooks/
   └─ pre-commit

这里有一个关键取舍：

不要建立 agents/agent-a/memory/...。

因为：

Agent ≠ Memory owner
Project = Memory owner
Agent = Memory accessor

今天 Agent A 做教学，明天 Agent B 接手教学，他们应该读到同一条 teaching memory line。

否则你最终会变成：

agent-a 对教学的记忆
agent-b 对教学的记忆
agent-c 对教学的记忆

然后还得解决三份记忆同步，这是反模式。

MEMORY.json

这是整个系统最重要的新文件，但应该非常小。

例如：

JSON
{
  "version": 1,
  "routing_policy": "fail_closed",

  "global_read": [
    "global/RULES.md"
  ],

  "projects": {
    "teaching": {
      "aliases": ["教学", "课程", "教案"],
      "path": "projects/teaching",
      "imports": []
    },

    "slides": {
      "aliases": ["课件", "PPT", "slides"],
      "path": "projects/slides",
      "imports": []
    },

    "memory-system": {
      "aliases": ["记忆系统", "memory", "agent memory"],
      "path": "projects/memory-system",
      "imports": []
    }
  }
}

这里故意没有搞复杂的权限系统。

最重要的只有三个概念：

project_id
path
imports

其中：

imports: [] 默认空。

也就是说：

项目之间默认完全不可见。

只有你明确声明：

JSON
"imports": ["slides"]

才允许某条线读取另一条线。

2. S-ID 怎么处理

你现有的 S-ID 可以保留，不建议为了新架构全部重编号。

但以后系统里的真正全局定位符定义为：

<project_id>::<S-ID>

例如：

teaching::S-0042
slides::S-0042
memory-system::S-0042

因此 S-ID 本身只需要在项目内唯一。

这样不用迁移旧数据。

INDEX 中记录：

JSON
{
  "items": [
    {
      "key": "teaching::S-0042",
      "sid": "S-0042",
      "kind": "state",
      "status": "active",
      "tags": ["assessment", "grade-7"],
      "updated_at": "2026-08-14",
      "file": "STATE.md",
      "anchor": "S-0042",
      "refs": [
        "teaching::S-0038"
      ]
    }
  ]
}

INDEX.json 绝不能成为新的真源。

它只是：

Markdown 真源的可重建索引。

所以：

Markdown = source of truth
INDEX.json = cache

删掉 INDEX 后运行：

memory.py rebuild-index

必须能够完全恢复。

3. 我建议的记忆分层

你提到人类记忆、CPU cache、递归记忆。

最适合你的其实是两者结合，但工程实现更接近 cache：

            GLOBAL KERNEL
              RULES.md
                  │
                  ▼
┌──────────────────────────────────┐
│ Project Namespace: teaching      │
│                                  │
│ L0  Working Memory               │
│     当前任务上下文，不入 Git       │
│             ↓                    │
│ L1  STATE.md                     │
│     当前事实 / 当前状态            │
│             ↓                    │
│ L2  DECISIONS.md                 │
│     为什么变成这样                │
│             ↓                    │
│ L3  CHANGELOG.md                 │
│     时间流水                     │
│             ↓                    │
│ L4  archive/                     │
│     历史冷记忆                   │
└──────────────────────────────────┘

它同时对应人类记忆：

工作记忆       → 当前任务
语义/长期记忆   → STATE
情景/因果记忆   → DECISIONS
时间经历       → CHANGELOG
弱化记忆       → archive

但是实现时不要使用这些模糊的人类概念判断。

Agent 真正执行的是明确规则：

L0 → L1 → L2 → L3 → L4
4. 读路由机制

这是整个系统最关键的部分。

我建议定一个原则：

先确定 scope，再允许 retrieval。

不要：

先搜索整个 repo
↓
再判断哪些内容和教学有关

应该：

用户任务
 ↓
确定 project_id = teaching
 ↓
限定 filesystem scope
 ↓
只在 projects/teaching 内检索

也就是：

Routing before Retrieval

而不是：

Retrieval before Filtering。

这一个决定能消灭大部分串台问题。

project_id 的判断优先级

固定为：

1. 调用时显式 --project
2. 当前任务/Skill 已绑定 project_id
3. workspace/path → MEMORY.json 映射
4. alias 唯一匹配
5. 无法唯一确定 → fail closed

第 5 条特别重要。

比如用户突然说：

“把刚才那个框架再优化一下。”

Agent 无法确定到底是教学还是记忆系统。

绝对不要猜。

此时：

project_id = UNKNOWN

允许：
global/RULES.md

禁止：
读取任何 project memory
写入任何 project memory

这就是：

Fail Closed

宁可少读，也不能串读。

5. Agent 默认读什么

例如当前：

project_id = teaching

默认启动读取顺序：

① global/RULES.md
② projects/teaching/STATE.md
③ teaching 中相关的 active DECISIONS

不要默认加载：

整个 DECISIONS
整个 CHANGELOG
archive
其他项目

换句话说：

正常任务

只需要：

GLOBAL
+
PROJECT STATE
+
相关 DECISIONS
深层读取规则

只有出现这些情况才向下查：

用户问“为什么？”

读取：

DECISIONS
用户问“以前怎么做的？”

读取：

CHANGELOG
用户明确问历史 / 某个旧 S-ID

读取：

archive/

于是 retrieval 具有一个非常简单的“逐层 page fault”逻辑：

STATE 足够？
    │
   yes → stop
    │
   no
    ▼
DECISIONS 足够？
    │
   yes → stop
    │
   no
    ▼
CHANGELOG
    │
    ▼
Archive

这比“每次启动把全部历史喂给 Agent”稳定得多。

6. 不用向量库，怎么查相关内容

你的规模完全没必要为了 retrieval 上向量数据库。

建议：

S-ID 精确检索
+
tags
+
status
+
ripgrep 全文搜索
+
INDEX.json

优先级：

S-ID > refs > tag > literal text

例如：

Bash
python scripts/memory.py read \
  --project teaching \
  --sid S-0042

或者：

Bash
python scripts/memory.py search \
  --project teaching \
  --query "assessment"

脚本内部第一件事不是搜索，而是：

Python
Run
root = manifest["projects"][project_id]["path"]

随后所有搜索限定：

projects/teaching/**

从物理路径上阻止串台。

7. 写路由：比读路由还应该严格

写必须遵循：

Single Write Scope

一次 memory operation 只能有一个目标项目。

例如：

WRITE_SCOPE=teaching

那么允许：

projects/teaching/*

禁止：

projects/slides/*
projects/memory-system/*
global/*
最重要的一条
Agent 不决定文件路径。

不要让 Agent 输出：

我要修改 ../../projects/teaching/STATE.md

应该让 Agent 只声明：

project = teaching
kind = state
sid = S-0042
operation = update

真正路径由 memory.py 决定：

Python
Run
target = route(project="teaching", kind="state")

返回：

projects/teaching/STATE.md

这样 Prompt Injection 或 Agent 自己犯糊涂，也跨不过 router。

8. CHANGELOG 最好取消“Agent 直接写”

你现在三个文件都由 Agent 操作的话，会产生一个隐患：

STATE 改了
DECISIONS 改了
忘记写 CHANGELOG

或者三处信息不一致。

所以我会直接定稿为：

Agent 可主动写
STATE
DECISIONS
Agent 不直接写
CHANGELOG
INDEX

由脚本自动生成：

memory write
      │
      ├── 修改 STATE / DECISIONS
      ├── 自动 append CHANGELOG
      └── rebuild/update INDEX

一次 semantic write：

1 operation
=
1 source mutation
+
1 changelog event
+
1 index update

这会明显减少维护成本。

9. “递归记忆”应该放在哪里

不要这样：

memory
 └ memory
    └ memory
       └ memory

真正适合你的递归结构只有：

S-ID → refs → S-ID → refs

例如：

S-0108
refs:
  - teaching::S-0031
  - teaching::S-0057

它形成一个轻量的记忆引用图。

因此需要追溯时：

S-0108
  ↓
S-0031
  ↓
Decision X

即可。

也就是说：

存储结构保持扁平，关系结构允许递归。

这是最容易维护的组合。

10. 记忆堆积：不要“删除”，而要改变默认可见性

这里建议借用人类遗忘机制：

遗忘 ≠ 数据消失
遗忘 = 检索成本提高 / 默认不再激活。

因此不要真正定期删除记忆。

使用：

HOT
WARM
COLD

三级。

HOT
STATE.md
active DECISIONS

每次 Agent 可读。

WARM
旧 Decisions
近期 CHANGELOG

按需读。

COLD
archive/

默认完全不读取。

11. STATE 应该有硬上限

STATE 最大的问题是非常容易最终变成第二个 CHANGELOG。

所以把定义写死：

STATE.md = 当前世界状态，不是历史。

推荐控制在大约：

30–50 个 active S-ID

如果一个 STATE 条目已经不再影响当前行为：

active
  ↓
superseded
  ↓
archive

而不是无限追加。

例如：

S-0042 当前课件结构采用 X

后来变成 Y：

不要：

S-0042 X
S-0088 Y

同时当作当前事实。

而是：

S-0042 superseded by S-0088
S-0088 active

默认 retrieval 只取：

status=active
12. DECISIONS 的处理

DECISIONS 不必像 STATE 那么激进。

状态推荐只有：

active
superseded
revoked

默认读取：

active
+
被当前 STATE 引用的 decision

旧 decision 可以继续存在，但不会自动进入上下文。

13. CHANGELOG 的处理

CHANGELOG 是最容易爆炸的文件，因此直接采用机械归档。

例如：

CHANGELOG.md

超过任一阈值：

500 条
或
3 个月

自动变成：

archive/changelog-2026-Q3.md

然后新建：

CHANGELOG.md

具体阈值不是重点。

真正重要的是：

Archive 不参与默认读取。

14. 不要搭定时任务：使用 Lazy Maintenance

你明确说不搭定时平台，这完全没问题。

所有维护动作都采用：

write-triggered maintenance

每次：

memory.py write

顺手检查：

STATE 是否超阈值？
CHANGELOG 是否超阈值？
INDEX 是否需要 rebuild？
broken refs？
重复 S-ID？

必要时执行归档。

因此没有：

cron
scheduler
后台服务
daemon

系统长期仍然能保持干净。

15. Skill vs 脚本：最终建议是混合，但职责必须分开

我会明确选：

Skill + Script 混合

但不是两套系统。

职责这样切：

Skill  = 大脑的行为协议
Script = 硬边界和执行器
Git    = 长期记忆介质
Skill 负责

告诉 Agent：

① 当前任务先确定 project_id
② 不允许跨 scope 检索
③ 默认只读 STATE
④ 为什么 → DECISIONS
⑤ 历史 → CHANGELOG/archive
⑥ 所有持久化操作必须调用 memory.py
⑦ 不得直接编辑 INDEX/CHANGELOG
⑧ scope 不明确时 fail closed

也就是说 Skill 是：

Memory Policy。

Script 负责
route
read
search
write
archive
index
validate

例如最终保持极少几个命令即可：

Bash
memory.py read
memory.py search
memory.py write
memory.py validate

甚至不要搞十几个子命令。

pre-commit 负责

最后一道保险：

S-ID 是否重复
project_id 是否合法
refs 是否存在
INDEX 是否匹配
文件是否放错 project
CHANGELOG 格式是否合法

于是完整链条是：

Agent
  ↓
Skill
  ↓
memory.py
  ↓
filesystem scope
  ↓
pre-commit
  ↓
Git

这已经足够强，不需要插件框架。

16. 为什么不推荐“插件优先”

插件比较适合：

API
数据库
远程服务
搜索服务
第三方系统

而你的 memory substrate 本质上就是：

Git repo + files

如果把它包装成插件，反而多了一层：

Agent
→ plugin runtime
→ API abstraction
→ files

收益很小，维护面变大。

所以：

Git 仓库是真源，Script 是 memory kernel，Skill 是 Agent adapter。

这是我认为最符合你“简单可维护”的长期形态。

17. 一个很重要的全局规则

global/ 一定要非常克制。

最危险的演化路径是：

项目不能串台
↓
那我把共同东西放 global
↓
越来越多东西进入 global
↓
所有 Agent 又开始读到所有东西

最后回到原点。

所以定义：

global 可以放
记忆系统规则
repo convention
全 Agent 都必须遵守的 invariant
真正跨所有项目的决定
global 禁止放
教学内容
某一份课件状态
memory-system 的设计细节
某个项目的 TODO

一个简单判断：

“如果删除其中一个项目，这条记忆是否依然成立？”

如果答案是否：

不能进 global。

18. 跨项目任务怎么办

例如：

“把教学项目的内容做成课件。”

这是合理的跨项目读取。

但也不要开放整个仓库。

显式声明：

primary_project = slides

read_scopes:
  - slides
  - teaching

write_scope:
  - slides

于是：

教学 = source
课件 = destination

Agent 可以：

READ teaching
READ slides

WRITE slides

但是不能顺手修改 teaching。

这叫：

Multi-read / Single-write

我强烈建议把它定成系统不变量。

19. 最终读写规则，可以压缩成 8 条

如果我要给你的 Skill 写“宪法”，核心实际上只有这些：

R1. 每个 memory operation 必须拥有 project_id。

R2. project_id 在 retrieval 之前确定。

R3. 默认只能读取：
    global + current project。

R4. 跨项目读取必须显式声明 read_scope/import。

R5. 一次操作只能有一个 write_scope。

R6. Agent 不指定 memory 文件路径；
    Router 根据 project + kind 决定路径。

R7. scope 不明确时 fail closed：
    可以不读，但不能猜着读/写。

R8. Archive 默认不可见；
    只有显式历史检索才进入 archive。

再加一条维护规则：

R9. CHANGELOG 和 INDEX 由脚本维护，
    Agent 不直接编辑。

做到这九条，串台风险已经会下降一个数量级。

20. 你这个系统最终应该长什么样

我会把整个架构概括成：

                    ┌─────────────┐
                    │ User Task   │
                    └──────┬──────┘
                           │
                    determine scope
                           │
                           ▼
                 ┌──────────────────┐
                 │ Memory Router    │
                 │ project=teaching │
                 └───────┬──────────┘
                         │
             ┌───────────┴───────────┐
             │                       │
           READ                    WRITE
             │                       │
      global/RULES            single project
             +                       │
     teaching/STATE                  ▼
             +                memory.py
      relevant DECISIONS             │
                                     ├─ STATE/DECISION
                                     ├─ CHANGELOG
                                     └─ INDEX
风险与需注意

最大的风险不是“检索算法不够聪明”，而是作用域不够硬。所以不要用 LLM 的语义判断代替 scope；“这个看起来像教学内容”只能作为辅助识别，不能成为授权依据。

第二个风险是 global 膨胀。它应该像操作系统 kernel，不是共享垃圾桶。

第三个风险是自动总结导致事实漂移。归档时可以移动、压缩索引，但不要让 Agent 自动把一大段历史“总结后删除原文”。原历史保留，摘要只是派生缓存。

第四个风险是多个 Agent 并行运行时使用一个全局 ACTIVE_PROJECT 文件。因此我反而不建议仓库里存在一个共享的 ACTIVE_CONTEXT.json。最安全的是每一次脚本调用显式带：

--project teaching

或者使用 Agent 自己的 session-local context；绝不能让多个 Agent 共享一个可变的“当前项目”。

第五个风险是 Skill 只是软约束。因此真正的安全性必须来自：

Skill 告诉 Agent 应该怎么做
+
Script 决定 Agent 实际能怎么做
+
pre-commit 抓最后的违规
最终定稿

如果由我来给 ai-hub-memory 定 v2 架构，我不会再增加新的记忆系统组件，而是在你现有架构上只增加三样：

① MEMORY.json：项目 namespace / routing manifest
② memory.py：所有持久记忆的唯一读写路由器
③ memory-router/SKILL.md：让不同 Agent 遵循同一套 memory protocol

然后把现有三件套移到：

projects/<project_id>/

并确立一个核心公式：

Memory = Global Kernel + Project Namespace + Layered Retrieval；Routing before Retrieval，Multi-read / Single-write，Fail Closed。

这套模型已经足够支撑你多个 Agent、多个项目长期运行，而且基本没有引入新的基础设施复杂度。
