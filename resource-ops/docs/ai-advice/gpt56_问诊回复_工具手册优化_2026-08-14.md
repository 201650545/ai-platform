六个问题的直接回答
1. 【结构】现在合理吗？要不要按任务场景组织？

当前结构合理，但建议升级，不建议推倒重来。

保留：

工具总览 → gh → lark-cli → opencli → gateway → 更新规则

这是工具手册最自然的维护结构，因为一个工具的命令、认证、坑应该只有一个权威位置。

但建议在“工具总览”前后增加两个很短的入口：

A. 常用任务速查

例如：

我要做什么	首选工具	操作前检查
GitHub 仓库/PR/Issue	gh	gh auth status
飞书表/文档/Bot	lark-cli	检查认证状态
操作已登录网页/AI	opencli	opencli doctor + session
多引擎 AI 搜索	gateway	health check

B. 首次使用检查

目的不是给高手看，而是防止弱模型一上来就复制正文中的写操作。

所以应该采用：

按场景做索引，按工具做正文。

不要把正文彻底改成“我要读表格”“我要搜索”“我要操作网页”这种场景章节，否则 opencli、lark-cli 等会在多个章节重复出现，后期更容易产生不一致。

而且 MEMORY.json 当前只把 global/RULES.md 和 global/DECISIONS.md 放进 global_read，没有强制每次加载 TOOLS，这一点我认为应该保持：TOOLS 本来就应该只在需要外部系统时 page-fault 式读取。

2. 【内容粒度】应该记到什么程度？“实测坑”值得保留吗？

我建议用一个标准判断：

删除这条之后，一个新 Agent 是否很可能犯重复错误，或者还得重新探索？

如果答案是“是”，就值得写。

应该写

核心能力。 一句话说明工具解决什么问题，不写完整产品介绍。

最少可用命令。 每个工具大约 3～7 条真正高频的命令即可。

Preflight / 自检命令。 比如 gh auth status、opencli doctor。

认证方式，但不记录认证材料。 如 keyring、浏览器已有 session、人工扫码。

成功信号。 弱模型尤其需要知道“什么结果才算成功”。

失败后的第一处理动作。 例如认证失效 → 停止并请求人工重新登录，而不是让 Agent 自己乱修。

高价值实测坑。 必须是可复现、会重复踩、对任务结果有明显影响的问题。

不应该写

完整 CLI --help 的复制品、低频子命令大全、一次性调试流水、具体 prompt 历史、长篇事故复盘、每个网站的所有账号/额度、不断变化的 session 状态，以及项目专属的 Base/Doc/Repo 使用说明。

你的 RESOURCES.md 已经是一个很大的资源台账，并承担了平台、额度、访问状态等信息；TOOLS 再复制这些东西，只会形成两个真源。 
GitHub

“实测坑”非常值得保留，但必须加生命周期

现在 opencli 四条坑很有价值。问题在于类似：

页面从 textarea 变 contenteditable

很可能随着版本升级失效。

因此建议每条坑最多包含：

现象 → 推荐处理 → Verified 日期/适用范围

例如：

[2026-08-14 / opencli 1.8.6] Windows 长文本注入：直接 CLI 参数可能解析异常；使用已验证的安全输入方式。版本升级后复测。

不要把“坑”变成无限追加的历史日志。过期坑直接删除即可——TOOLS 是当前运行手册，不是 CHANGELOG。

登录态/Session 状态：不要把文档变成实时数据库

这是我最建议改变的一点。

现在：

已登录 / 未登录 / 可能未运行

容易让下一模型误认为这是当前事实。

应改成：

认证模式：keyring
运行时状态：volatile，使用前必须检查
检查：gh auth status
last_verified: 2026-08-14

也就是说：

记录验证办法，弱化最后状态。

对于 Chrome session、账号池、:3000 在线状态，甚至可以完全不维护“当前状态”，每次需要使用时现场检查。

是否机制化？

或者：

python scripts/toolcheck.py gh
python scripts/toolcheck.py opencli
python scripts/toolcheck.py gateway

只做：

版本 → 可执行文件存在 → auth/session/health → 输出 READY / AUTH_REQUIRED / DOWN / UNKNOWN

按需调用、不常驻、不定时、不自动 commit。

只有发生持久变化时才修改 TOOLS，例如：

认证方式改变；

CLI 主版本升级导致命令变化；

4. 【跨模型可用性】如何让最弱模型也能照着用？

要加，而且“最少可用命令集”比继续增加知识更重要。

现在最大的问题之一是：

lark-cli base ...
lark-cli doc ...
lark-cli im ...

对熟悉环境的人足够，但对弱 Agent 来说，... 意味着它仍然不知道下一步是什么。 
GitHub

我建议每个工具统一采用 6 格操作卡：

用途：什么时候选它
Preflight：先运行什么
最小命令集：3～5 个
成功标准：看到什么算成功
STOP 条件：什么情况下禁止继续猜
坑/Fallback：失败第一步怎么办

再增加一个 首次使用检查清单：

确认任务应该用哪个工具；

读该工具章节；

先执行只读 Preflight；

确认当前账号/项目/session 范围正确；

先读后写；

遇到认证、scope、未知页面结构时停止猜测；

写操作遵守 global/RULES 和项目规则。

尤其要增加 STOP 条件。

较弱模型最大的风险往往不是“不知道命令”，而是：

命令失败 → 自己猜参数 → 再猜账号 → 再猜路径 → 最终做错。

因此手册应该明确：

UNKNOWN ≠ READY。核验失败就停，不根据旧状态推断当前状态。

这实际上就是你记忆系统现有 Fail Closed 思想在工具层的延伸。

5. 【安全边界】除凭证外还应该禁止什么？

建议把红线扩成以下几类。

① 所有认证材料。

不仅是 API key/token/password，还包括：

session token；

refresh token；

cookie 值；

OAuth code；

Authorization header；

浏览器 session 导出；

localStorage 中可恢复身份的值；

扫码二维码内容；

私钥。

尤其当前 TOOLS 提到镜像站通过 localStorage 登录，这里应该只记录“认证依赖浏览器已有 session”，不要记录 localStorage 的认证内容或整块 dump 方法。 
GitHub

② 私人账号细节。

原则上不写手机号、邮箱、账号池成员明细、内部用户 ID。

像 GitHub owner/repo namespace 这种执行命令确实需要、且本身非秘密的标识可以保留；但不要形成“账号资产档案”。

③ 公共仓库里的内部网络拓扑。

如果这个 GitHub 仓库是公开的，我建议避免保存：

内网 IP；

私有 hostname；

管理后台 URL；

tunnel URL；

带认证参数的 URL；

内部服务发现信息。

localhost/:3000 这类单纯端口本身风险较低，但也应尽可能用逻辑名描述。

④ 不必要的绝对本机路径。

当前 TOOLS 直接出现：

D:\项目\services\search_gateway

这既暴露本机目录结构，也很容易换机器就失效。 
GitHub

建议改成：

service: search_gateway
locator: 见环境 bootstrap / workspace 配置

如果必须提供路径，优先仓库相对路径或环境变量，而不是用户名、本机盘符相关绝对路径。

⑤ 会泄露秘密的诊断输出。

手册可以写“运行诊断命令”，但不要教 Agent 把：

全部环境变量；

完整 localStorage；

cookie jar；

credential store；

直接 dump 到聊天/日志。

⑥ 高风险写操作。

工具手册应该标记：

READ / WRITE / DESTRUCTIVE

删除、覆盖、发消息、push、修改外部表等操作，应统一指向全局确认规则，而不是每个工具自己再写一遍。

你现有 AGENTS.md 已经规定执行前确认，并且全局安全区已经有 pre-commit secret scanning、禁止凭证进 Git 等机制；TOOLS 应该引用这些规则，而不是复制出第二套规则。
