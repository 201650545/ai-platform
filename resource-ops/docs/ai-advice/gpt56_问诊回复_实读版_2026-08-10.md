# 建议方案（逐问题给，可改动我原来的设计）

## 1\. 多维表格设计

### 结论

**六表保留，密钥池必须独立；但现有六表再改一版 v0.3。**

当前“资源能力 + 资源实例”拆分非常正确：能力定义一次，多个实际入口独立记录额度、凭证和健康状态，调度器因此可以只换实例而不换逻辑模型。[GitHub+1](https://github.com/201650545/ai-resource-hub/blob/main/docs/%E5%A4%9A%E7%BB%B4%E8%A1%A8%E6%A0%BC%E8%AE%BE%E8%AE%A1%E6%96%B9%E6%A1%88.md)

### 表 1：账号资产

建议增加：

-   `account_id`：稳定唯一键，不要拿平台名称当关系键。

-   把现在的“登录方式=已登录”拆成两个字段：

    -   `auth_method`：密码 / OAuth / 微信 / 手机等。

    -   `session_state`：LOGGED\_IN / EXPIRED / NEEDS\_HUMAN。

-   `browser_profile_ref`：只记录本地 Chrome profile 的逻辑 ID，不记录 cookie。

-   `last_session_verified_at`

-   `next_session_verify_at`

-   `human_action_reason`


当前记录已经证明“登录方式”和“当前登录状态”实际上是两种概念，例如 Kimi 是“密码/微信/短信”但当前未登录。[GitHub](https://github.com/201650545/ai-resource-hub/blob/main/docs/%E8%B5%84%E6%BA%90%E8%B0%83%E7%A0%94/%E9%AA%8C%E8%AF%81%E8%AE%B0%E5%BD%95_2026-08-10.md)

### 表 2：凭证池

**保留独立表，但只管认证，不管资源额度和路由。**

建议字段：

`credential_id / account_id / credential_type / status / expires_at / local_secret_backend / last_local_check_at`

删除：

**`轮换组`。**

另外，“代金券/免费权益”不应该被视为 Credential。凭证回答的是“我凭什么认证”；免费额度回答的是“这个实例还能用多少”。这两个生命周期完全不同。

### 表 3：资源能力规格

现在最需要重构。

保留：

`capability_id / canonical_model / quality_tier / exec_type / verification_policy`

增加：

`adapter_id / protocol_version / auth_scheme / allowed_hosts / model_family / request_schema_version / health_probe_id`

不建议继续把：

`{"Authorization":"Bearer {{CREDENTIAL}}"}`

这种可执行 Secret 模板作为飞书配置。当前方案确实这样设计。[GitHub](https://github.com/201650545/ai-resource-hub/blob/main/docs/%E5%A4%9A%E7%BB%B4%E8%A1%A8%E6%A0%BC%E8%AE%BE%E8%AE%A1%E6%96%B9%E6%A1%88.md)

正确边界应该是：

**飞书：**

`adapter_id = openai-compatible`
`auth_scheme = bearer`
`allowed_host = api.xxx.com`

**本地 adapter：**

知道如何取 credential，并只允许把它加到匹配的受信 host。

这样即便 AI 把 endpoint 改成恶意地址，也拿不到 Secret。

### 表 4：资源实例

这是调度器真正主要读取的表。

建议补结构化额度字段：

`quota_total`
`quota_remaining_snapshot`
`quota_unit`
`quota_reset_policy`
`quota_reset_at`
`quota_expires_at`
`safety_margin`
`rate_limit_rpm/tpm`
`route_priority`
`provider_model_name`
`config_version`

当前的“免费额度描述=2000万 token / 180天”适合人看，不足以让调度器执行；实例表现在虽然已有剩余额度/重置日，但仍缺单位、硬停止阈值和重置规则。[GitHub+1](https://github.com/201650545/ai-resource-hub/blob/main/docs/%E5%A4%9A%E7%BB%B4%E8%A1%A8%E6%A0%BC%E8%AE%BE%E8%AE%A1%E6%96%B9%E6%A1%88.md)

`routing_group` 最好只有一个真源：

> **推荐直接用 `capability_id` 作为默认 routing group。**

只有以后出现“同一个 canonical model 需要人为分成两个独立池”时，才增加单独的 `route_policy_id`。

### 表 5：工具资产

现阶段可以不动。

以后如果 AI 真要自动调用工具，再把它升级成类似 Capability 的结构化规格，否则当前 8 字段作为资产目录足够。[GitHub](https://github.com/201650545/ai-resource-hub/blob/main/docs/%E5%A4%9A%E7%BB%B4%E8%A1%A8%E6%A0%BC%E8%AE%BE%E8%AE%A1%E6%96%B9%E6%A1%88.md)

### 表 6：任务日志

现在已经有 `idempotency_key / lease / attempt / evidence`，方向正确。[GitHub+1](https://github.com/201650545/ai-resource-hub/blob/main/docs/%E5%A4%9A%E7%BB%B4%E8%A1%A8%E6%A0%BC%E8%AE%BE%E8%AE%A1%E6%96%B9%E6%A1%88.md)

但“避免重复验证”的真正幂等键建议改成：

`task_type + target_id + verifier_version + target_config_hash`

而不是单纯：

`task_type + instance_id + verification_version`

再增加：

`target_config_hash`
`result_code`
`evidence_hash`
`sync_state`
`created_by`
`supersedes_task_id`

**最重要的一条：UNIQUE 和 lease 在 SQLite 做，飞书只同步结果。**

建议再增加 4 个视图：

-   `无健康备份能力`

-   `额度即将耗尽`

-   `配置冲突`

-   `同步失败 / 待回写`

## 2\. 调度器形态

**本地单进程 + `127.0.0.1` base\_url 代理 + SQLite，就是目前最简且正确的形态。不要先上微服务、Docker 编排或独立网关集群。**

仓库当前也是这一设计。[GitHub](https://github.com/201650545/ai-resource-hub/blob/main/%E6%96%B9%E6%A1%88%E4%B9%A6.md)

内部拆成 6 个模块即可：

`Proxy → Router → Provider Adapter → Quota Ledger → SQLite → Sync/Outbox`

核心路由原则建议变成：

> 客户端请求 canonical model → 找该 capability 的健康 instances → 安全过滤 → 排序 → 选实例 → 本地 adapter 注入凭证 → 调用。

错误也必须分类，而不能笼统 fallback：

-   `quota_exhausted` → EXHAUSTED

-   `429/rate_limit` → COOLDOWN

-   `401/403` → CREDENTIAL\_INVALID

-   `model_not_found` → CONFIG\_INVALID

-   `5xx/network` → 短暂失败，可切同能力实例

-   质量/模型不匹配 → **禁止切换**


还有一个容易遗漏的原则：

**流式响应一旦已经向客户端输出内容，就不要再透明换实例重放。**

只有“尚未输出任何客户端可见字节”时才允许安全切换，否则可能出现重复回答和重复计费。

## 3\. Open CLI 与飞书回写闭环

建议不要设计成：

`Open CLI → 直接写飞书`

而是：

`Open CLI → SQLite 任务结果 → Outbox → 单写者 → 飞书`

完整闭环：

**发现 → 创建任务 → SQLite UNIQUE 去重 → SQLite lease → Open CLI 执行 → 结构化结果 → 同一事务更新 instance + task + outbox → 单写者回飞书 → ACK**

仓库已经提出状态机、lease、单写者和结构化 evidence，这是对的。[GitHub](https://github.com/201650545/ai-resource-hub/blob/main/%E6%96%B9%E6%A1%88%E4%B9%A6.md)

这样飞书断网时不会丢验证结果：

`task = SUCCEEDED`
`sync_state = PENDING`

恢复后继续回写即可。

避免重复验证使用三层门：

1.  `next_verify_at > now` → 不验证。

2.  已有相同 `target_config_hash + verifier_version` 的成功任务 → 不验证。

3.  SQLite `UNIQUE(idempotency_key)` → 并发 Agent 只能成功领取一个。


`NEEDS_HUMAN` 后应进入**阻塞状态**，不能自动不断重试，直到人工明确清除该状态，这与当前方案的人工介入原则一致。[GitHub](https://github.com/201650545/ai-resource-hub/blob/main/%E6%96%B9%E6%A1%88%E4%B9%A6.md)

## 4\. 画布两功能优先级

**HTML 运营可视化先做，AI 搜索聚合后做。**

仓库 v0.2 当前顺序就是这样，我赞成。[GitHub](https://github.com/201650545/ai-resource-hub/blob/main/%E6%96%B9%E6%A1%88%E4%B9%A6.md)

但第一版甚至不要做“大画布”，只需要回答：

**当前用哪个实例？还有几个同模型备用？哪个快没额度？哪个 cooldown？哪个需要人工？哪个验证过期？**

因为这是检验整个调度器是否可信的窗口。

搜索聚合只有等：

`候选 → 验证 → 去重 → 入库`

闭环稳定后才有价值。

否则搜索能力越强，得到的只是越来越大的“未经验证候选垃圾场”。

## 5\. 安全模型

凭证 ID + 本地读取只是第一层。

我认为最容易被忽略的最高风险不是 `credentials.json` 本身，而是：

**配置注入导致 Secret 被合法代码发送到错误地址。**

必须补：

-   Secret 只能由可信本地 adapter 注入，飞书不能指定 Secret 的任意传输模板。

-   credential 必须绑定 `allowed_hosts`；跨域 redirect 不继续携带 Authorization。

-   Open CLI 浏览网页得到的文字一律视为“不可信输入”，网页不能修改 Secret policy。

-   Browser executor 最好使用单独 Chrome Profile，避免接触日常密码管理器、其他登录账号和无关 cookie。

-   `credentials.json`、SQLite、dump、backup、shell history、环境变量、调试日志、遥测、代理 access log 都属于泄漏面。

-   飞书 token、GitHub token 本身也属于 Secret。

-   公共 exporter **必须从零构造白名单 DTO**，不要先序列化内部对象再做 blacklist 删除。

-   `备注 / error / evidence / URL query` 等自由文本默认不得进入 public JSON。

-   Secret scanner 应放在**出站边界**：日志、飞书同步、Git commit、AI context 四处都检查。


你现在方案已经覆盖日志、截图、clipboard、AI 上下文和公开数据白名单，这是很好的基础。[GitHub](https://github.com/201650545/ai-resource-hub/blob/main/%E6%96%B9%E6%A1%88%E4%B9%A6.md)

## 6\. 问诊机制 / GitHub 数据桥

**GitHub Public JSON 很适合作为“可审计的架构快照”，但不应该成为实时运行数据总线。**

仓库目前明确设计为：飞书 → 白名单脱敏 → GitHub Pages/Public JSON → 高级模型读取。[GitHub+1](https://github.com/201650545/ai-resource-hub/blob/main/%E6%96%B9%E6%A1%88%E4%B9%A6.md)

这个方案对于“每次架构升级让高级模型问诊”已经够好。

ChatGPT 官方 GitHub 集成当前确实可以读取授权仓库里的代码和文档，但 OpenAI 也说明仓库发现/索引存在延迟，而且可用性会随套餐和使用体验不同，所以它并不适合作为秒级运行态接口。[OpenAI Help Center](https://help.openai.com/en/articles/11145903-connecting-github-to-chatgpt%2525252525252525253B.xls?utm_source=chatgpt.com)

我建议最终采用**双桥**：

**桥 A：GitHub snapshot**

用于：

`架构问诊 / 历史 diff / 审计 / fallback`

文件建议：

`manifest.public.json`
`capabilities.public.json`
`health.public.json`

每个都有：

`schema_version`
`generated_at`
`source_revision`
`content_hash`

只在语义变化时 commit，不要按每次 API 调用更新 Git。

**桥 B：Read-only MCP / API**

只暴露少量脱敏查询：

`search_catalog()`
`get_capability(id)`
`get_health_summary()`
`get_architecture_snapshot()`

OpenAI 当前官方文档已经支持远程 MCP 作为 ChatGPT/Deep Research 等的数据接入方式；Anthropic 的 MCP connector 也支持通过 HTTP 连接远程 MCP。[OpenAI Developers+1](https://developers.openai.com/api/docs/mcp?utm_source=chatgpt.com)

因此最佳形态不是“用 MCP 替掉 GitHub”，而是：

> **GitHub = 可版本化公开档案；MCP = 高效查询接口。**

对于当前阶段，**先保留 GitHub，不急着做 MCP**。

## 7\. 里程碑

仓库现在真正的 M1→M6 已经不是你问题里最初的：

`调研→凭证库→调度器→飞书→画布→全链路`

而已经改成：

`双实例切换 → SQLite/观察 → 飞书同步 → HTTP 自动验证 → Open CLI → AI 自主调研`

# 风险（每条一句话）

-   **Secret 路由风险：** 飞书可配置任意 endpoint/header 时，受污染配置可能把本地凭证发送给错误主机。

-   **模型偷换风险：** 若 canonical model 与 provider model 映射没有程序级断言，供应商别名变化可能产生隐性模型切换。

-   **额度超支风险：** 本地 token 估算与厂商账单存在误差时，没有 safety margin 会突破“额度到点即停”的承诺。

-   **并发风险：** 若把 Feishu lease 当锁，多 Agent 会因为飞书写冲突产生重复任务；官方 API 本身不适合这一职责。[Feishu](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/update?lang=zh-CN&utm_source=chatgpt.com)

-   **同步风险：** SQLite 成功而飞书失败时，没有 outbox 会形成不可恢复的双真源分叉。

-   **浏览器风险：** Open CLI 使用日常 Chrome Profile 会把整个浏览器身份面扩大到资源调研任务。

-   **提示注入风险：** 第三方网页内容可能诱导 Agent 修改配置、访问非目标域或暴露敏感上下文。

-   **公开桥风险：** 自由文本字段进入 GitHub Public JSON 时可能间接泄漏账号、余额、内部 URL 或错误上下文。

-   **重复验证风险：** 只依赖日期或 fingerprint、没有配置版本哈希时，配置变化与验证结果无法正确失效。

-   **复杂度风险：** 过早开发搜索聚合/MCP/漂亮 dashboard 会推迟真正证明“自动停、同模型自动切换”的核心价值。

# 需确认（你拿不准、需要永涛拍板的点）

1.  **“同模型”的判定到底多严格。** 我建议由永涛维护明确的 `canonical_model` 映射白名单；名称相似绝不自动视为同模型。

2.  **不同 provider 对同一底模但量化、上下文长度、工具调用能力不同，是否允许互切。** 如果答案是“不允许能力下降”，那么 canonical model 还不够，routing compatibility 必须同时锁 `context/tool/vision/reasoning` 等能力特征。

3.  **免费额度与付费余额谁优先。** “不偷偷省钱”意味着调度器不能自行把“便宜”理解成最高优先级，需要永涛明确：到期优先、免费优先、主渠道优先，三者如何排序。

4.  **是否接受独立 Chrome Profile。** 我强烈建议 Open CLI 用专门的“资源运营 Profile”，但这会稍微降低“直接使用日常登录态”的便利性。

5.  **凭证保存后端。** M1 用 `credentials.json + 严格本地权限` 足够；长期是否升级到系统 Keychain/Secret Store，需要永涛决定复杂度是否值得。

6.  **Public Read Model 的实时性要求。** 如果问诊只是架构评审，GitHub 足够；只有需要分钟级读取最新健康状态时，才值得增加 MCP。

7.  **是否允许“同模型但不同第三方中转品质”的实例进入同一路由组。** 这是“不降质”承诺中最需要永涛亲自拍板的边界；我建议默认 **不自动认为等价，必须经过验证后显式加入 compatibility group**。
