3. 【整理触发】定时 vs 按需怎么调和？

我建议：

不做真正的 wall-clock 定时任务。

因为仓库已有全局决策：

工作模型 = 按需调度；不做定时提醒/汇报平台。

而且 AGENTS §4 同样明确写了“不搭定时提醒/汇报平台”。
GitHub

建议改成 三触发 + 一个日界线检查：

T1 会话/项目启动：
   memory.py status
   → 发现昨天以前 pending
   → 标记 settle_due

T2 数量阈值：
   pending >= 20
   → settle_due

T3 用户显式：
   “整理记忆”
   → 立即 settle

T4 写项目正式记忆前：
   如存在相关 pending
   → 顺手归并

其中所谓“每天处理”实现为：

今天第一次调用 memory.py
        ↓
last_settle_date < today ?
        ↓ yes
显示：昨日 staging 待整理

这叫 lazy daily consolidation。

它：

不需要 cron；

不需要 GitHub Actions；

不需要服务器；

不需要后台 daemon；

又基本保持“每天有整理周期”。

我认为它比真正定时更符合你目前整个系统哲学。

如果以后你真的决定“每天 02:00 无人值守自动整理”，那就应该明确 SUPERSEDES 当前“不做定时平台”的全局决策，而不是暗中加一个 cron。

4. 【数据结构】隔离记忆怎么设计？

我建议一条记忆一个文件。

不要每天一个大 JSONL/Markdown。

原因之一是你仓库自己已经指出：两个 Agent 同时向同一 append-only 文件 EOF 追加仍可能产生 Git conflict。
GitHub

推荐：

inbox/
├── pending/
│   ├── 2026-08-14/
│   │   ├── I-20260814T081532-A7F2.md
│   │   ├── I-20260814T083001-B319.md
│   │   └── ...
│   └── 2026-08-15/
│
├── settled/
│   └── 2026-08/
│       ├── I-20260814T081532-A7F2.md
│       └── ...
│
└── receipts/
    └── 2026-08/
        └── I-20260814T081532-A7F2.json

我不建议：

001-teaching-xxx.md

把 project 写进文件名。

因为 staging 的核心就是归属可能变化：

UNKNOWN → courseware

如果项目名在文件名里，每次重分类还得 rename。

应该让文件名只有不可变 ID，project 放 metadata：

YAML
---
id: I-20260814T083001-B319
captured_at: 2026-08-14T08:30:01
project_hint: UNKNOWN
routing_basis: none
kind_hint: state
source_scope: session-local
---

用户决定以后所有课件默认使用 16:9。

注意：

不要保存整段聊天记录。

只保存“可成为记忆的最小事实”。

否则 inbox 很快从“海马体 staging”退化成“聊天日志备份库”。

另外凭证要在 capture 写文件之前检查，而不能只依赖现有 pre-commit。当前 check_memory.py 确实会扫描 staged secrets 并阻止 commit，但那已经发生在文件被创建之后；你的红线是“不进记忆文件”，所以 ingress 必须提前拒绝。
GitHub

5. 【整理算法】UNKNOWN 怎么处理？整理后怎么办？

推荐 settle 做六步：

Step A — 拉最新
Bash
git pull --ff-only

与当前仓库的串行化规则一致。
GitHub

Step B — 安全过滤

首先检查：

credential?
token?
secret?
明显无长期价值？

凭证直接拒绝进入系统。

Step C — 判断“值不值得记”

这是非常关键的一层。

不要因为进了 inbox 就必然升级成长期记忆。

AGENTS 当前本来就规定，中间探索过程、一次性内容、不再复用内容不应该正式写记忆。
GitHub

所以：

candidate
 ├─ discard
 ├─ merge existing
 ├─ STATE
 └─ DECISION

这正是“海马体式 consolidation”真正有价值的地方。

Step D — 定项目

优先级建议继续沿用 R1/R2 的思想：

1. 用户明确说过项目
2. 当前 task/Skill 绑定
3. workspace/path
4. MEMORY.json alias
5. 明确的已有 routing metadata
6. 内容模型只做 candidate recommendation
7. 仍不确定 → UNKNOWN

前四类都属于较可靠的路由依据，当前 Skill 已经定义类似优先级。
GitHub

关键规则：

内容判断可以推荐 project，但不能用低置信语义猜测突破 fail closed。

例如：

“PPT 第4页字体改大”

模型可提出：

candidate: courseware

但如果内容是：

“以后这个课程都按这个结构”

teaching/courseware 都可能成立，就留 UNKNOWN。

UNKNOWN 不要求立刻逐条问用户。

应该累积起来，在适当时候批量问：

以下 4 条无法可靠归类：
I-xxx → teaching / courseware ?
I-yyy → memory-system / 新项目 ?
...

一次解决。

Step E — 巩固

正式写：

STATE
DECISIONS

必要时合并旧条目，而不是复制重复事实。

Step F — 留痕

原始 capture 文件：

pending/.../I-xxx.md

原样移动到：

settled/YYYY-MM/I-xxx.md

另外创建：

JSON
{
  "id": "I-xxx",
  "disposition": "promoted",
  "target_project": "courseware",
  "target_kind": "decision",
  "target_id": "D-COURSE-20260814-03",
  "settled_at": "2026-08-14"
}

这样：

Raw episode   → 不改
Settlement    → 单独留 receipt
Project memory→ 精炼后的事实

这是我最推荐的留痕方式。

6. 【四层记忆整体】最终形态怎么划分？

我建议不是“4 个都每次读取”，而是 4 个生命周期层 + 分层检索策略。

L0 工作记忆 Working Memory

位置：

Agent 当前上下文

特点：

当前任务推理；

临时信息；

未确认判断；

不进 Git；

生命周期分钟～小时。

L1 短期 / 隔离记忆 Staging

位置：

inbox/pending/

特点：

episodic candidate；

可以不知道项目；

尚未获得“正式记忆”资格；

高频写、短生命周期；

每日/阈值 consolidation；

UNKNOWN 在这里合法存在。

它对应的更像：

海马体临时编码区。

L2 中期项目记忆 Project STATE

位置：

projects/<project>/STATE.md

特点：

当前项目有效状态；

当前目标；

卡点；

下一步；

最近完成；

稳定 S-ID；

是热状态投影，不是历史仓库。

这和现有仓库定义完全吻合：STATE 有 60 行/12KiB/最近完成 8 条限制，过期状态不能凭年龄自动删，而需要 DROP。
GitHub

热长期：

五、推荐协议条文

我建议不要推翻 R1-R9，而是做一个 v2.1 精确化。

其中 R1 必须改一下，否则 persisted UNKNOWN 在文字上仍然违规：

R1' 项目正式记忆的读写必须携带明确 project_id；
    staging capture 必须携带 capture_scope，
    project_hint 可以为 UNKNOWN。

再增加：

R10. Staging 是候选记忆区，不属于任何项目正式记忆线；
     UNKNOWN 不等于 global。

R11. Staging 读取仍遵循作用域隔离：
     默认只允许 current_project + same-origin UNKNOWN，
     禁止项目 Agent 全量读取 UNKNOWN。

R12. Settle 前必须完成正式 project routing；
     无法可靠确定项目的条目继续留在 UNKNOWN，
     不得凭语义猜测突破 Fail Closed。

R13. 一次 settle 写入只能落一个 project write_scope；
     settle-plan 可以跨项目读取规划，但不得跨项目实际写入。

R14. Staging 不是聊天日志。
     只有可能复用的记忆候选才能 capture；
     consolidation 可 discard / merge / promote。

R15. 凭证、key、token 在 capture 写文件之前即拒绝；
     不允许依赖 commit 阶段才过滤。

R16. 不建立常驻定时服务；
     采用日界线检查 + 数量阈值 + 用户显式触发的按需 consolidation。

这样原来的核心公式仍成立：

Memory
=
Global Kernel
+ Project Namespace
+ Layered Retrieval
+ Quarantined Ingress

而不是：

Memory
=
所有 Agent 都能看的巨大共享池
风险（每条一句话）
