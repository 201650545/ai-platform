我建议把生命周期控制在三个简单机制里：

STATE：硬限额。 ≤60 行、≤12 KiB、最近完成 ≤8 条；超出直接由 hook 拒绝。旧“已完成”不再另建 STATE archive，而是 DROP 出热状态，其历史已经存在于 CHANGELOG + Git。

CHANGELOG：滚动文件。 建议“月度或 200 条，先到者触发”，归档到 archive/changelog/YYYY/。归档是冷却，不是删除。

DECISIONS：低频滚动 + 有效决策前置。 不建议机械按月切，建议约 80 个决策或 100 KiB 时才归档；同时给决策增加稳定 D-ID，归档后仍然有效的长期决策以简短引用留在热文件。

还有一个很重要的协议措辞需要修改：归档与“文件永远 append-only”在字面上是冲突的。 应把不变量从“这个路径永远不能删除旧行”升级为：

历史记录 immutable；正常写入 append-only；唯一允许删除热文件旧记录的情况是 ROTATE，且被移出的记录必须原样进入 archive，同一 commit 完成。

这样既保住不可变历史，也真正能控制主文件体积。

我建议把“不可用临界点”和“应该提前治理的阈值”分开：

文件	建议开始治理	大致开始难用	原因
STATE.md	60 行 / 12 KiB	100+ 行	每次接手都读，是最高频热数据
已完成（最近）	8 条	15–20 条	完成历史会挤掉真正重要的进行中/卡点/下一步
DECISIONS.md	80 条 / 100 KiB	150–300 条	每次新项目都要求读，token/注意力污染明显
CHANGELOG.md	200 条 / 200 KiB	500–1000+ 条	默认不读，所以容忍度最高，但 grep/人工回溯逐渐变差

这里的数字不是 Git 的技术极限——Git 处理远大于这些文件完全没问题；这是人和 Agent 的认知热路径极限。

当前 CHANGELOG.md 已经出现“一条流水占非常长一行”的模式，因此对它来说字节数/条目数比物理行数更有意义。
GitHub

如果现在这种项目启动期写入密度持续一年，CHANGELOG 达到上千条完全可能；但无需等到“不可用”才处理，200 条左右就滚一次成本最低。

2. CHANGELOG / DECISIONS 怎么归档而不破坏不可变历史？
CHANGELOG：非常适合滚动归档

是的，archive/ 是正确姿势。

例如：

archive/
└── changelog/
    ├── 2026/
    │   ├── CHANGELOG-2026-08.md
    │   ├── CHANGELOG-2026-09.md
    │   └── ...

建议规则：

月度 OR 200 条 OR 200 KiB，先到者触发。

但不是做定时任务；在下一次正常写记忆时发现达到条件，再执行 rotation，这符合 AGENTS 的“按需调度、不搭定时提醒/汇报平台”。
GitHub

DECISIONS：不能简单照搬 CHANGELOG

这是最大的区别。

协议要求 Agent 新项目开始时读 DECISIONS.md，目的就是“用户已经拍板的事情别推翻”。
GitHub

假如你把一年前一个仍然有效的架构决策机械移进 archive，而 Agent 默认又不读 archive，就可能再次讨论甚至推翻它。

所以推荐：

历史 decision record 进入 archive/decisions/；

每个新决策增加稳定 D-ID；

仍然有效的长期约束在当前 DECISIONS.md 保留简短 active reference；

已被替代的决策使用新决策写 SUPERSEDES D-xxx，旧记录不改；

真正完整原文仍在 archive。

例如当前这类“按需调度”“四文件共享记忆”“禁止 force push”就明显属于长期有效项，而不是一个月后应该彻底从热读取消失的东西。当前 DECISIONS 中确实存在这类长期决策。
GitHub

Git 历史还完整吗？

完整。

只要：

archive 与主文件在同一个 repo；

归档过程本身 commit；

不 reset --hard + force push；

不做 history rewrite；

那么旧内容既存在 archive 的当前树里，也存在过去 commit 中。AGENTS 本身已经禁止共享历史的 force-push 改写。
GitHub

注意：归档不会显著缩小 .git 仓库大小。 它解决的是热文件大小、阅读成本和检索噪声，不是 Git object 存储量。这个正符合你说的“冷却，不是新的记忆系统”。

“最近刚做完什么？”

同时不会把 STATE 变成第二个 CHANGELOG。

第 9 条完成出现怎么办？

不是：

STATE → archive/state/……

而应该：

1. 新完成项进入 已完成（最近）
2. 最旧 completed S-ID 淘汰
3. CHANGELOG 写：
   DROP S-202608xx-xx — completed recent-window rollover;
   completion retained in CHANGELOG
4. 从 STATE 删除

不要建立 STATE archive。

因为 STATE 本身就是“当前状态投影”；完成事件已经有 CHANGELOG，旧 STATE 快照又天然存在 Git 历史里。

否则你最终会造出：

STATE
STATE archive
CHANGELOG
CHANGELOG archive

等于人为制造第二套历史，违背“保持简单”。

4. 进行中 / 下一步过期怎么办？最后更新日期 + 超期标记是否值得？

思路是对的，但我不建议要求 Agent 手工维护每条 last_updated。

因为会产生这种低价值维护：

[S-x] xxx | updated=2026-08-14

Agent 每次只是确认“还有效”，就必须改日期，反而制造 commit 噪声。

更轻的做法是：

S-ID + Git 自己充当最后修改时间。

脚本找到某个 S-ID 所在行，再通过 Git blame / commit timestamp 得到它最后一次真正被修改的时间。

默认建议：

进行中：14 天没变 → STALE warning
下一步：30 天没变 → STALE warning
卡点：30 天没变 → STALE warning

这里 STALE 只 warning，不 block commit。

真正需要 Agent 做的只有四种选择：

仍有效      → 不动 / 明确 KEEP
状态变化    → 更新原 S-ID 内容
已完成      → 转最近完成
废弃/失效   → CHANGELOG DROP → 从 STATE 移除

这样“时效检查”发生在正常 memory commit 时，不需要任何定时平台。

最重要的一点：

过期时间只是要求复核，不代表自动删除。

否则 30 天没碰但仍然极重要的项目约束会被错误清掉，与现有“未知条目默认保留”的防覆盖原则正面冲突。AGENTS 明确要求只有明确完成、失效或被新事实取代才允许删除。
GitHub

5. 完整记忆生命周期：新建 → 活跃 → 归档 → 可选删除

建议定义成下面四阶段。

新建

满足 AGENTS 的写入条件才创建记忆：

可交付单元完成
用户拍板
共享状态发生别人必须知道的变化

而探索过程、一次性内容、本地细节不写。这个现有入口过滤器其实就是第一道“防膨胀”，应该继续严格执行。
GitHub

状态：

STATE       → S-ID
DECISION    → 建议新增 D-ID
CHANGELOG   → event
活跃
STATE       = 当前事实
DECISIONS   = 当前仍值得接手 Agent 看到的决策 + 最近决策
CHANGELOG   = 当前热流水段

通过：

ff-only；

重读最新 STATE+DECISIONS；

S-ID 保留；

DROP；

credential scan；

size guard；

维持。

归档

只有历史日志进入 archive：

CHANGELOG old segment → archive/changelog/
DECISION old record   → archive/decisions/

STATE 不另建 archive。

Archive 文件一旦创建，hook 禁止普通 commit 修改。

可选删除

这里我建议非常保守。

对 STATE：

DROP 就是逻辑删除，Git/CHANGELOG 保留历史。

对 archive：

默认永不物理删除。

因为 git rm archive/foo.md 并不真正从 Git 历史删除它，反而减少了当前树可检索性，却几乎没有安全收益。

只有法律/隐私/误提交敏感数据这种特殊情况才考虑真正 history rewrite；但你的凭证红线已经要求凭证压根不能进 commit，因此正常 ILM 完全无需进入这一复杂路径。AGENTS 目前也明确把凭证误提交视为 key rotation 问题。

Hook 检查规则

保留现有两项：

[BLOCK] 暂存内容出现疑似 credential
[BLOCK] STATE S-ID 消失且 CHANGELOG 无 DROP

新增：

[BLOCK] STATE.md > 60 physical lines
[BLOCK] STATE.md > 12 KiB
[BLOCK] 已完成（最近） > 8 entries

[WARN]  进行中 S-ID > 14d 未修改
[WARN]  下一步 S-ID > 30d 未修改
[WARN]  卡点 S-ID > 30d 未修改

[BLOCK] 修改/删除已经存在的 archive/* 文件

[BLOCK] CHANGELOG 删除旧记录，
        但相同记录没有出现在本次新增 archive/changelog/* 中

[BLOCK] DECISIONS 删除旧记录，
        但相同记录没有出现在本次新增 archive/decisions/* 中

[WARN/BLOCK] CHANGELOG > 200 entries 或 >200 KiB → 要求 rotate
[WARN/BLOCK] DECISIONS > 80 decisions 或 >100 KiB → 要求 rotate

这里我倾向：

达到归档阈值先 WARN；超过阈值 25% 再 BLOCK。

例如 CHANGELOG：

200 → warn
250 → block

这样不会因为正在交付一个关键任务，突然被维护性操作卡死。

归档命令

正常入口仍然遵守现协议：

Bash
git pull --ff-only

然后：

Bash
python scripts/rotate_memory.py changelog
python scripts/rotate_memory.py decisions

git add CHANGELOG.md DECISIONS.md archive/
git diff --cached

git commit -m "memory: rotate archive"
git push

rotate_memory.py 只需要做很少的事：

1. 找到满足归档条件的完整记录
2. 原样写入新的 archive 文件
3. 从 hot file 移除对应记录
4. 不修改历史记录正文
5. 输出归档条数和目标文件

它不要自动 commit，不要自动 push。Git 操作继续由现有流程控制。

对于月边界，也不需要 cron：

下一次正常写记忆
→ check_memory 发现上一月份仍在 hot changelog
→ 提示 rotate
→ 本次顺手归档

完全符合你现有“按需调度”。

- CHANGELOG 建议在月切换或达到 200 条时归档；
  DECISIONS 低频归档，以 80 条为建议阈值。

  STALE；STALE 只要求复核，不得自动删除。删除仍必须满足 DROP 规则。

  CORRECTION / SUPERSEDES 记录，不回写旧记录。

我还建议给未来 DECISIONS 增加稳定 ID：

[D-20260814-01]

以后变更用：

[D-20260902-01] SUPERSEDES D-20260814-01 — ...

这样决策归档之后仍能无歧义引用，而且和你已经验证有效的 S-ID 思路一致。

风险

DECISIONS 过度归档：长期有效决策如果从热读取完全消失，会让新 Agent 重复讨论甚至推翻旧拍板。

按月归档过细：低频 DECISIONS 每月一个文件会产生大量小文件，建议按量/半年。

STATE 只设行数不设字节数：一行几千字仍能绕过“一页纸”，因此行数与 KiB 要双限。

STALE 自动删除：绝对不要做，时间老不等于事实失效。

hook 自动修改文件：不建议，hook 应检查和拒绝，实际整理交给显式脚本。

archive 可任意修改：会把“不可变历史”退化成普通 Markdown 文件，因此已提交 archive 应由 hook 锁定。

把 STATE 历史再复制一遍归档：会制造两个历史源，增加而不是降低记忆复杂度。

把“归档”误认为瘦 Git：旧对象仍在 Git 历史，归档只降低热读取成本。

需确认

我认为真正需要你拍板的只有 3 个参数/语义：

是否接受把 append-only 的定义从“路径永不删行”改成“记录 immutable，ROTATE 是唯一允许移出热文件的例外”。这是启用真正归档的前提；否则严格字面 append-only 与控制主文件体积无法同时成立。

STATE 硬限额是否采用 60 行 / 12 KiB / 最近完成 8 条。我推荐直接定死，之后不再凭感觉判断“一页纸”。

DECISIONS 是否增加稳定 D-ID + SUPERSEDES。我推荐加；这样它才能安全经历几年归档而不丢决策身份。

其余我建议直接定为默认：CHANGELOG 200 条触发归档、250 条硬阻断；DECISIONS 80 条提示归档；STALE 只 warning；STATE 不建 archive；archive 已提交文件禁止修改。
