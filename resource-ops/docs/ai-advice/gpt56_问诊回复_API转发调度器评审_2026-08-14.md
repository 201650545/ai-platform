C. 调度器本身的几个实际坑
1. credentials.json → Authorization 方案本身没问题，但还缺一层“凭证域隔离”

本地文件可以继续用，不需要为了“安全”强行上 Vault。

最低要求：

credentials.json:
- chmod 600
- 不进 Git
- 不记录 Authorization header
- 不记录完整 request headers
- crash dump / debug dump 不带 secrets

更重要的是：

credential 必须绑定固定 provider/upstream allowlist。

例如：

YAML
siliconflow-main:
  provider: siliconflow
  allowed_hosts:
    - api.siliconflow.cn

转发时：

Python
Run
assert parsed_upstream.hostname in credential.allowed_hosts

否则如果哪一天配置文件或管理接口被改成：

upstream=https://evil.example.com
cred=siliconflow-main

你自己的调度器就会主动把 Bearer key 发送给恶意服务器。

同时建议：

verify TLS = true
禁止跨 host redirect 携带认证
upstream 不能由客户端请求参数指定

这比把 credentials.json 换成另一个文件名重要得多。

2. 你真正应该建模的是 account，不只是 instance

这是现在设计里最值得改的一点。

例如：

siliconflow-main
 ├─ DeepSeek-V4-Flash
 └─ GLM-5.2

这两个 instance 消耗的是同一个 SiliconFlow 账户余额。

所以：

remaining_quota

不能只挂 instance。

应该分成：

ProviderAccount
Credential
ModelEndpoint
RouteInstance

例如：

YAML
account:
  id: siliconflow-account-1
  provider: siliconflow

credential:
  id: siliconflow-main
  account_id: siliconflow-account-1

instance:
  id: inst-siliconflow-deepseek-v4-flash
  credential_id: siliconflow-main

而：

充值余额
赠送余额
月度消费

是 account-level。

API key 是否有效
key spending cap

才可能是 credential-level。

model price
context window

是 model endpoint-level。

这也直接回答你的“同一厂商多个 key 是否支持”：应该支持，但不要把多个 key 自动理解为多个独立额度池。

例如模型 A：

模型 B：

Python

    estimated_uncached_input_tokens * input_price
    + estimated_cached_tokens * cached_price

7. Failover 必须区分“请求错误”和“实例错误”

推荐：

400 / 422 参数错误
→ 默认不要 failover
→ 返回客户端

401
→ disable credential

402 / insufficient balance
→ disable account until positive balance probe

403 permission/model entitlement
→ disable model endpoint 或 credential

429
→ Retry-After / temporary cooldown

500/502/503/504
→ short circuit breaker + failover

OpenRouter 官方也指出 429/503 可携带 Retry-After。
OpenRouter

尤其是 streaming：

在第一个 token 发给 localhost 客户端以前，可以 failover；一旦已经输出部分 SSE，不能偷偷切另一家然后继续拼。

因为那可能产生两套不同答案。OpenRouter 自己也明确采用这个边界。

provider_account

P2 — 再做动态价格排序。
