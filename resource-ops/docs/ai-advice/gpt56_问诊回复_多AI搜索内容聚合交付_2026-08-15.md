一、总评（<200字）

方向正确，而且应继续做减法：不要把“文字池”做成新系统，也不要把 AI 搜索内容硬塞进 LLM 网关。建议采用 Agent 编排 + 现有搜索 SSE + 每任务 JSONL 内容池 + 静态单 HTML 报告。SSE 只负责显示搜索进度，内容在后端汇总，完成后生成 HTML 给用户点击查看。当前规模无需数据库、消息队列、React 或复杂服务化。

二、五问直接回答
1. 架构：文字内容池用什么？
结论

当前首选：内存 + JSONL 文件。暂时不要 SQLite。

三者定位应该这样理解：

方案	建议	用途
内存队列	✅ 用，但不是最终存储	接住 4 个 AI 并发返回
JSONL 文件	✅ 当前主存储	简单、可追加、可恢复、可调试
SQLite	暂时不要	大量历史任务、检索、多人并发后再上

不要使用一个巨大的 pool.json 反复整体读写，建议使用 JSONL：一行一个记录。

例如每次任务：

runs/
  20260815_001/
    raw.jsonl
    merged.json
    report.md
    report.html

每条记录统一成：

JSON
{
  "run_id": "20260815_001",
  "provider": "kimi",
  "event_id": "kimi-18",
  "title": "...",
  "url": "...",
  "text": "...",
  "timestamp": "..."
}
多 AI 并发不要让四个线程直接抢着写文件

建议：

豆包 ─┐
元宝 ─┤
Kimi ─┼→ 内存 Queue → 单 Writer → raw.jsonl
秘塔 ─┘

也就是：

多生产者 + 单写入者。

Python 中一个 asyncio.Queue 或普通 queue.Queue 就够了。

这样无需处理复杂的文件锁。

去重不要做得太“智能”

建议分三层：

SSE 事件去重

provider + event_id

防止 SSE 重连造成重复写入。

来源去重

URL 标准化后去重。

删除 utm_* 等跟踪参数。

文本精确去重

规范空格、换行后计算 SHA-256。

Hash 相同则合并。

不要一开始做向量相似度/Embedding 去重。

尤其豆包和 Kimi 对同一个问题给出相似观点，并不意味着应该删掉其中一个；“不同 AI 都这么认为”本身就是信息。

所以建议：

只消灭真正重复的数据，不消灭不同 AI 的重复观点。

是。当前这是最佳方案。

建议最终：

CSS 全部：

直接写进 HTML。

3. 交互：动态流程用什么技术栈最轻量？
推荐的不是“纯动态”和“纯静态”二选一，而是：

搜索阶段动态，结果阶段静态。

架构：

浏览器
   │
   │ SSE：只收状态
   ↓
Agent / Search Hub
   │
   ├─ 豆包搜索
   ├─ 元宝搜索
   ├─ Kimi 搜索
   └─ 秘塔搜索
        ↓
     Queue
        ↓
    raw.jsonl
        ↓
   normalize / merge
        ↓
    report.html
        ↓
SSE: report_ready
        ↓
浏览器显示：
「查看完整报告」

前端甚至只需要几十行 JS。

状态可以显示：

正在搜索……

✓ 豆包完成
✓ Kimi 完成
● 元宝处理中
✓ 秘塔完成

正在整理内容……

✓ 报告已生成

[查看完整报告]

这比单纯一个无限旋转圈更好。

因为一个转圈转 30 秒，非技术用户很容易怀疑“是不是死了”。

SSE 传什么？

不要再通过 SSE 给页面传全部搜索内容。

只传：

JSON
{
  "provider": "kimi",
  "status": "done"
}

以及：

JSON
{
  "status": "report_ready",
  "url": "/reports/20260815_001.html"
}

搜索内容全部在服务器端处理。

这样你现有 SSE 基础设施可以继续复用，但 UI 会简单很多。

技术栈

现在甚至没必要为了这件事情上：

React

Vue

WebSocket

Redis

Celery

继续：

HTML + CSS + 原生 JS + Python 后端 + SSE

即可。

如果现有 multi_ai_search_hub 已经有 SSE 服务，继续使用那个 SSE 服务，不要重新搭一套。

python http.server 主要负责最后生成好的静态 HTML 即可。

4. API 转发：怎么统一转到文字池？

这里是我认为你当前设计里最值得修改的一点。

不建议：
AI 搜索
 ↓
my_ai_gateway
 ↓
文字内容池

因为 my_ai_gateway 的职责本来是：

LLM API 渠道路由。

而 AI 搜索返回内容属于：

搜索结果数据流。

这是两个不同层次的问题。

硬塞进去会慢慢把 gateway 变成：

模型路由
+ 搜索路由
+ 数据存储
+ 内容汇总
+ Agent 通信

后面反而越来越难维护。

更简单的方案

如果 Agent 本身就是总执行者：

Agent
 │
 ├─ 调 multi_ai_search_hub
 │       ↓ SSE
 │
 ├─ 收集结果
 │
 ├─ 写文字池
 │
 ├─ 调 my_ai_gateway（可选）
 │       ↓
 │    做摘要/综合
 │
 └─ 生成 HTML

也就是说：

Agent 就是胶水层。

甚至不需要新增“转发 API”。

这是当前最简单的架构。

如果两个项目必须继续完全独立进程运行，那么才增加一个极小接口：

http
POST /ingest

内容：

JSON
{
  "run_id": "...",
  "provider": "kimi",
  "event_id": "...",
  "text": "..."
}

然后：

multi_ai_search_hub
       ↓
POST /ingest
       ↓
collector
       ↓
JSONL

这个 collector 可以只有几十到一两百行 Python。

不需要经过 OpenAI-compatible gateway。

Gateway 什么时候出现？

只有需要 LLM 做：

综合摘要；

去杂；

章节整理；

标题生成；

多 AI 共识/分歧提取；

才：

merged content
      ↓
my_ai_gateway
      ↓
某个可用 LLM
      ↓
最终整理文本

这就保持了两个现有项目的边界：

Search Hub
负责：找东西

Gateway
负责：调用 LLM

Agent
负责：编排

Content Pool
负责：暂存

Renderer
负责：交付

这个职责划分比较干净。

底层实际存在一个：

因此既可以 URL 浏览，也可以直接把 HTML 文件发给用户。

对系统

建议每个任务实际保留四个文件：

但用户正常情况下只接触：

report.html

或者它对应的 URL。

系统交付是一组文件，用户交付是一个 URL / 一个 HTML。

把：

四、风险
1. HTML 注入 / XSS

这是最值得提前处理的。

AI 搜索结果本质属于不可信输入。

例如返回内容里出现：

HTML
<script>...</script>

绝对不能直接拼进报告执行。

Python 输出 HTML 前至少做：

Python
Run
html.escape(text)

如果将 Markdown 转 HTML，也要限制或过滤原始 HTML。

原则是：

搜索得到的 HTML 只能当文字，不能当程序执行。

2. SSE 重连导致重复

浏览器或服务断线后可能重放事件。

因此每个事件带：

event_id

写池前判断：

run_id + provider + event_id

是否已经存在。

3. 四家搜索结果完成时间不同

不要因为一个失败导致整份报告失败。

例如：

豆包 ✓
元宝 ✓
Kimi × 超时
秘塔 ✓

仍然生成 HTML，并写明：

本次获得 3/4 个搜索渠道结果，Kimi 搜索超时。

这对真实产品非常重要。

4. 去重过度

最危险的不是“有两段相似内容”，而是：

把两个 AI 独立给出的相同结论当垃圾删掉。

因此只做：

完全重复事件；

完全相同 URL；

完全相同文本；

不要第一版做语义级强去重。

5. LLM 综合产生幻觉

如果通过 Gateway 再让一个 LLM 总结四家的结果，应明确要求：

只能依据输入；

保留分歧；

不补充未经搜索得到的事实；

引用 provider/source。

HTML 最好同时保留：

综合报告
+
各 AI 原始输出

而不是只给综合摘要。

6. 一个 HTML 最终可能很大

当前只有四家 AI，基本不是问题。

以后如果出现：

很多图片；

几十 MB 内容；

附件；

上百次搜索；

再考虑：

report/
  index.html
  data.json
  assets/

现在不要提前解决这个问题。

五、需拍板点

实际上我认为只剩 4 个决策需要现在拍板：

用户最终交付：选 HTML。
MD 作为内部中间产物保留，不作为默认用户界面。

文字池：选 Queue + JSONL。
现在不上 SQLite；未来出现大量历史检索/多人并发再迁移。

Gateway 不承担搜索内容转发。
Agent 直接消费 Search Hub SSE → Content Pool；Gateway 仅负责真正需要 LLM 的“整理/总结”。

产品交互定为“动态过程 + 静态结果”。
SSE 页面显示四个平台处理状态；全部/部分完成后生成单文件 report.html，出现一个明显的 「查看完整报告」 按钮。

如果按“最简单可落地”排序，第一版甚至只需要增加三个东西：collector.py、renderer.py、一个 HTML 模板；你现有的 multi_ai_search_hub 和 my_ai_gateway 都不用大改。
