§3
问题二：调度器与网关是否该整合

      

结论：不做仓库级合并；做「逻辑整合、物理分离」。

      
现状与定位：ai-hub 的网关（:3000，opencli 控 5 引擎搜索）已运行；ai-resource-hub 的本地调度器（M1）
尚未建成
（README 标 ⏳）

[4]

。两者职责本质不同——调度器是
资源分配决策
（读台账，决定本次调用用哪个 key/模型），网关是
请求转发执行
。决策与执行分层本身就是对的。

      
反对仓库级合并的三个理由：

      

        

域隔离
：资源域（台账/凭证/额度）与操作域（转发/搜索/编排）耦合后，改网关代码就要碰资源仓库，任何操作面事故都可能波及资源真源。

        

时机不对
：调度器未成形，过早合并等于把一个未验证的组件搬进另一仓库，返工成本高。

        

真源唯一
：资源数据的真源必须留在 ai-resource-hub（与 F2 的修法同向），调度器只是它的消费者。

      

      

        
建议 R1 · 逻辑整合、物理分离

        调度器实现为 
ai-hub 网关内的一个模块
（或旁路轻脚本）：网关每次出站调用前问调度器「本次用哪个 key/model」，调度器输出决策 + 依据；数据侧只读 ai-resource-hub 的公开 JSON（额度模糊化版）或本地 
scheduler/credentials.json
（信任平面）。代码住操作面、数据留资源面、接口单向只读——把这条约定写进两个 README 的边界段即可，不需要动仓库结构。

§5
问题四：16 条宪法 + 5 分法是否有漏洞

      
先肯定完备的部分：
Routing before Retrieval、Fail Closed、Quarantined Ingress（隔离暂存）、R15 无痕删除禁令、R16 双道凭证防线（落盘前 preflight + pre-commit 兜底）、防膨胀窗口（STATE ≤60 行/完成 8 条、单条 600 字、CHANGELOG 200 条归档）
——这套组合对纯文本体系的常见失败模式（乱归属、猜路由、静默删史、凭证泄漏、无限膨胀）均有针对性拦截，成熟度高

[3]

。以下漏洞按重要性排序：

      
5.1 漏洞 A（关键）：并发写防护停留在协议层，未下沉到脚本

      

        
发现 F3 · 并发写风险

        RULES 要求「改记忆前先 
git pull --ff-only
」，但这只是协议约定。实测 
scripts/memory.py
：含 git subprocess 封装，但 
write/settle 路径未强制 pull
。两个 Agent 同时 pull → write → push 时，后推者要么 merge conflict，要么
S-ID 撞号
（ID = 项目 + 当天日期 + 递增序号，同日并发必撞）。单人单窗口时风险低，多 Agent 并行时必然暴露。
      

      

        
建议 R2 · 把「先 pull」从协议降为脚本强制

        在 
write/settle
 命令内部自动执行 
git pull --ff-only
，失败（远端有新提交/分叉）即
拒绝写入并提示重试
——与 Fail Closed 原则完全同构，改动量小、收益最大。
      

      
5.2 漏洞 B：全局决策与项目决策冲突时无优先级规则

      
global 的「删项目测试」（删除任一项目这条记忆是否仍成立）是很好的准入判据，但 16 条宪法没有一条规定
冲突时谁赢
。建议补一条（新增 R17 或并入 R5）：「项目域内冲突时项目决策胜出，global 只维护跨项目 invariant」。

      
5.3 漏洞 C：inbox 冷启动（可接受，标注即可）

      
R14 明确不建 cron / GitHub Actions / daemon——符合体系「不引入定时平台」的约束，这个取舍是对的。代价是自动触发只剩「会话/项目启动检查」：长期无会话则 inbox 无限增长（pending≥20 / UNKNOWN≥5 是整理触发条件，不是容量上限）。个人系统风险低，建议接受现状，仅在 
status
 命令输出中增加「inbox 超阈值已停留 N 天」的显式提醒。

      
5.4 5 分法评价与轻微瑕疵

      

RULES=MUST / PROJECTS=WHERE / RESOURCES=WHAT / TOOLS=HOW / STATE=NOW，DECISIONS 隐式承担 WHY——五分法本身无结构性漏洞
。唯一的张力即 F2：RESOURCES 这一层与 ai-resource-hub 的真源声明冲突，修法见 R3（指针化）。另一处轻微瑕疵：MEMORY.json 中 memory-system 的别名含通用词 
memory
，与课件/教学语境撞词面较大——好在 R7 Fail Closed 有兜底（歧义留 UNKNOWN 累积后问用户），可接受，无需改动

§7
风险与需确认事项

      
风险

      

        

双真源腐化已在发生
：RESOURCES.md 的额度是 08-13 快照，今天读取即可能失真——越晚指针化，错误决策（如按旧余额选模型）的概率越高。

        

并发写风险随 Agent 并行度上升
：当前单人节奏风险低；一旦两个窗口同时做记忆写入（sync 批量导入时最可能），撞号/conflict 即出现。

        

本地克隆陈旧是系统性隐患
：本次审查开头本地即落后 34 个提交。任何 Agent 不 pull 就读，都会拿到完全错误的结构认知。

        

private 仓库模式外推风险
：公开 JSON 消费模式对 english-teaching-production 不适用，路由文档需显式声明，防止新 Agent 误推公开。

      

      
需用户确认的三个决策点

      

        

数据桥收敛方向
：同意以 feishu-data-hub 为唯一管道（R4）？exporter 是彻底退役，还是保留一层薄封装做资源表的模糊化预处理？

        

RESOURCES.md 指针化
：同意 R3 吗？代价是 memory 侧资源信息变薄（只剩结论与指针），换来真源唯一、不再腐化。
