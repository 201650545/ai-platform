结论（一页以内总评）

你现在的四文件分层思路是对的：STATE.md 做短期快照、DECISIONS.md 保存用户约束、CHANGELOG.md 保存历史流水，读路径很短；仓库目前也确实按这个模型执行，STATE.md 明确采用“单写者 + 整体覆盖”，AGENTS 规定写前 git pull。
GitHub
+1

但当前协议有一个关键缺口：

Git 能检测“提交历史冲突”，不能检测“语义上的旧快照覆盖新快照”。

例如 A 已把“任务 X 完成”写入 STATE.md 并 push；B 随后 git pull 得到了最新版，但 B 根据自己旧的上下文重新生成整份 STATE，没有保留 X。这个提交在 Git 看来完全合法，因为 B 的提交本来就是基于 A 的最新 commit，因而可能没有 merge conflict、没有 push 错误，却发生静默记忆丢失。这是目前最大风险。
GitHub
+1

另一方面，CHANGELOG.md / DECISIONS.md 的 append-only 也不能天然解决并发。两个 Agent 从同一个 commit 开始追加时，第一个 push 成功后，第二个直接 push 通常会被 Git 的 non-fast-forward 规则拒绝；第二个 pull/rebase 时，如果双方修改同一 EOF 区域，仍可能产生文本冲突。你自己的 AGENTS.md 已经正确指出了这一点。
GitHub
+2
Git
+2

我的建议不是现在就上“每 Agent 分记忆 + 专门记忆 Agent”。 对目前 2–5 Agent、低频写，这明显偏重。当前最优解是：

继续四文件架构，但把“整体重写 STATE”升级为“基于最新 STATE 的保留式更新”，再增加一个 immutable update/event 作为保险层。

到几十 Agent、高频写时，再演进成：

Agent 只写互不冲突的 immutable event 文件 → Memory Agent 按需汇总 → STATE/DECISIONS 变成只读投影。

也就是说，未来适合“主 + 分”，但“分”最好不是每 Agent 一份不断增长的记忆文件，而是每次交付一个不可变 event 文件。这样并发性质更好，也不会产生新的共享热点。

四个问题的直接回答（编号对应）
1. 「写」的时候会发生记忆覆盖/丢失吗？

会，而且有两种不同问题。

第一种是 Git 层并发冲突。

假设 A、B 同时：

A pull ── 修改 ── commit ── push ✓
B pull ── 修改 ── commit ───────── push ✗ non-fast-forward

Git 默认不会让 B 直接覆盖已经前进的远端分支，所以第二个 push 会失败；B 必须重新 fetch/pull/rebase。
Git
+1

因此：

“写前 git pull”不是锁，也不等于真正串行化。

A 和 B 完全可能在同一秒都 pull 到版本 N。

第二种才是更危险的 语义覆盖：

N:
进行中：X

A pull N
A 完成 X
A 写 STATE：
  已完成：X
A push -> N+1

B pull -> 得到 N+1

但 B 根据自己的旧上下文重新生成整个 STATE：
  已完成：Y

B push -> N+2，正常成功

此时 X 消失。

Git 不会报错。

因为从 Git 的角度：

N -> A(N+1) -> B(N+2)

历史完全线性。

所以当前 STATE.md = 整体重写 必须增加一条核心规则：

STATE 不允许从 Agent 自己的上下文重新生成；必须先读取 pull 后磁盘上的最新 STATE，在其基础上做“保留式更新”。未知条目默认保留，只有明确完成、失效或被新状态取代的条目才能删除。

你现在的 STATE 已经是典型短快照，而且包含多个此前交付成果，因此这种“保留未知事实”的规则非常重要。
GitHub

至于 append-only：

同一个 CHANGELOG.md 并发 append 仍可能 conflict。

你的 AGENTS.md 对这一点已经写对了；Git merge 遇到无法自动处理的修改会停止等待解决，而不是因为“都是追加”就自动保证安全。
GitHub
+1

2. 是否应该设计「主记忆 + 分记忆」？

方向正确，但不建议现在实施，而且建议稍微改模型。

不要优先设计成：

Claude.md
ChatGPT.md
Kimi.md
Executor.md
        ↓
Memory Agent
        ↓
STATE.md

因为“按 Agent 分片”其实是在按生产者组织数据，而你的真实读写原子是项目/可交付单元。

以后同一个 Agent 可能并发执行多个项目，同一个项目也可能连续经过多个 Agent；按 Agent 文件最终还是需要重新解释上下文。

更合理的是：

events/
  20260814T101501Z__claude__xxx.md
  20260814T101743Z__kimi__yyy.md
  20260814T102012Z__executor__zzz.md
              ↓
        Memory Agent
              ↓
        STATE.md
        DECISIONS.md

每个 event 是一个已经完成的可交付事实，而不是 Agent 的“个人日记”。

例如：

YAML
id: 20260814T101501Z-claude-a81f
agent: claude
project: ai-hub
type: delivery
status: done
summary: resources_bridge 回归完成
next: 无

然后一两行正文即可。

这样有四个优势：

不同 Agent 创建不同文件，没有“大家同时修改同一个 EOF”的热点。

event 一旦 commit 就不修改，天然适合 Git。

即使 STATE 汇总错了，原始事实仍在，可以重建。

Memory Agent 可以成为唯一 STATE 写者。

第二个并发 push 仍可能因为远端分支已经前进而被拒绝，但重新 rebase 后，不同路径的新增文件通常不存在同一文件的文本冲突；所以它解决的是内容热点，而不是取消 Git 的并发控制。
Git
+1

而且 Memory Agent 不需要定时运行。完全符合你的“按需调度”红线：

发现待折叠 events
→ 用户下一次开始项目 / Agent 需要最新主记忆
→ 按需调用 Memory Agent
→ 汇总
3. 当前规模和未来规模各自最优架构？

当前 2–5 Agent、低频写：不要上完整主+分架构。

最优是：

四文件 + Freshness Barrier（新鲜度屏障）+ Preserve Merge（保留式更新）+ Push Retry。

也就是说先把现有设计补正确。

核心不是“真正做到绝对只有一个 Agent 能写”，而是让并发发生时失败可见、恢复确定、不能静默丢数据。

未来几十 Agent、高频写：

Immutable Events + 单写者 Projection。

把 Git 仓库当一个很轻量的 event log：

Agent → immutable event
Agent → immutable event
Agent → immutable event
             ↓
       Memory Agent
             ↓
    STATE / DECISIONS

此时 STATE.md 不再是真源，而是物化视图 / materialized view。

真正的可恢复真源是：

Git history + immutable events

这比“几十个 Agent 都直接改 STATE”可靠得多。

4. 有没有比「主+分」更轻量的折中？

有，而且这是我最推荐你现在采用的方案：加一个 UPDATES/ 保险箱，而不是完整分记忆。

文件结构：

AGENTS.md
STATE.md
DECISIONS.md
CHANGELOG.md

UPDATES/
  20260814T101501Z__claude__a81f.md
  20260814T103022Z__kimi__be92.md

每次交付：

① pull 最新
② 重新读 STATE + DECISIONS
③ 创建一个唯一的 UPDATES/<id>.md
④ 基于最新 STATE 做保留式更新
⑤ 有决策再追加 DECISIONS
⑥ CHANGELOG 追加
⑦ commit
⑧ push

这样即使第④步哪个 Agent犯错，把 A 的信息从 STATE 删了：

UPDATES/A.md

仍然存在。

也就是说：

STATE 是缓存；UPDATES 是保险。

这只增加一个目录，没有长期运行的 Memory Agent，也没有每 Agent 独立记忆体系，我认为是当前规模下性价比最高的折中。

推荐方案（当前规模 + 未来规模各一套，可直接落地到 AGENTS.md/文件结构）
当前规模：方案 A「四文件 + Event 保险」

建议目录：

/
├─ AGENTS.md
├─ STATE.md
├─ DECISIONS.md
├─ CHANGELOG.md
└─ UPDATES/
   └─ YYYYMMDDTHHMMSSZ__agent__random.md

其中职责定义为：

AGENTS.md
协议。

STATE.md
一页纸当前快照。
允许重写，但必须基于最新版本做“保留式更新”。

DECISIONS.md
用户拍板决定。
只追加。

CHANGELOG.md
近期操作索引。
只追加；过长后按月滚动归档。

UPDATES/
每个可交付单元一个不可变事实记录。
创建后禁止修改/删除。
平时不读，仅用于并发保险、审计、恢复。

建议把 AGENTS.md 中现有：

git pull 最新 → 改文件 → commit → push

升级成：

写入协议：

1. 工作区必须 clean。
2. git pull --ff-only，取得最新远端版本。
3. pull 完成后必须重新读取 STATE.md + DECISIONS.md；
   禁止仅根据当前对话中的旧副本写 STATE。
4. 先创建本次交付对应的唯一 UPDATES/<event-id>.md。
5. 更新 STATE 时：
   - 默认保留最新 STATE 中自己无法确认应删除的内容；
   - 只修改本任务明确影响的状态；
   - 只有“已完成 / 已失效 / 被新事实取代”的条目允许删除；
   - 禁止从零根据 Agent 自身上下文重建 STATE。
6. DECISIONS / CHANGELOG 继续 append-only。
7. commit。
8. git push。
9. 若 push 因远端前进失败：
   禁止 force push；
   重新同步远端、重新读取最新记忆、重新合并本次变化，再 push。
10. 有任何无法判断的语义冲突时，不自动选择 ours/theirs，
    保留双方事实并标记待确认。

--ff-only 的价值是：拉取阶段如果历史已经分叉，不偷偷产生一个你没注意到的 merge，而是直接停下来；而 push 端继续依靠 Git 的 fast-forward 约束阻止直接覆盖远端历史。
Git
+1

其中最重要的一句话，我会直接放进协议加粗：

Git conflict 只能发现文本/历史冲突，不能发现语义覆盖；因此 STATE 必须基于 pull 后的磁盘最新版做保留式修改，禁止根据 Agent 旧上下文整页再生成。

Agent 的权限模型变成：

普通 Agent：
    可以 CREATE event
    不允许修改已有 event
    不直接修改 STATE
    不直接修改 DECISIONS

Memory Agent：
    唯一可以重写 STATE
    唯一可以维护 DECISIONS 投影

写路径：

Agent 完成交付
       ↓
create memory/events/<unique-id>.md
       ↓
commit + push

Memory Agent 按需执行：

读取上次 checkpoint 后的新 events
              ↓
        语义去重 / 冲突检测
              ↓
       重写 STATE.md
       更新 DECISIONS.md
              ↓
          commit + push

可以在 STATE.md 顶部保存一个非常便宜的 checkpoint：

source_commit: abc1234

这里记录的是上一次汇总所覆盖的父 commit。

下一次 Memory Agent 只需：

Bash
git diff --name-only abc1234..HEAD -- memory/events/

就可以定位上次汇总以后新增的事件，而不必重新读全部历史。

这完全建立在 Git 自身的 commit DAG 与 diff 能力上，不需要数据库。

未来我甚至建议：

CHANGELOG.md

不再由几十个普通 Agent 共同 append。

因为 event 本身已经承担：

谁
什么时候
完成什么

再维护 CHANGELOG 会变成重复数据 + 写热点。

可以让 Memory Agent 生成一个“最近 N 条”的 CHANGELOG.md 投影，完整历史仍然留在 immutable events + Git 中。

DECISIONS.md 也存在同样问题：真正永久 append-only 的一个文件最终一定违反“一页纸”约束。

未来最好变成：

decision event = 永久历史
DECISIONS.md   = 当前仍然有效的用户决策，一页纸

例如旧决定被用户明确推翻时，不删除历史 event，而只让当前投影显示：

D017：使用方案 B
supersedes: D004

这样同时得到：

不可篡改历史 + 一页纸当前上下文。

风险（每条一句话）

STATE 静默覆盖： Agent 即使成功 pull/push，也可能因为使用旧语义上下文重建 STATE 而删除别人刚写入的信息。

伪串行化： pull → edit → push 是乐观并发而不是锁，两个 Agent 可以同时从同一个版本开始工作。

EOF 冲突： 多 Agent 同时 append CHANGELOG.md 或 DECISIONS.md 仍可能在 merge/rebase 阶段冲突。
GitHub
+1

错误解冲突： Agent 自动采用 ours/theirs 可能把一个合法事实直接丢掉，因此记忆冲突应采用“双方保留、语义判断”原则。

强推风险： 任何普通 Agent 使用 force push 都可能绕过 Git 的 fast-forward 保护，记忆仓库应明确禁止。
Git

日志无限增长： 当前永久 append-only 的 DECISIONS/CHANGELOG 最终必然与“一页纸”目标冲突。

Memory Agent 单点： 未来专门汇总 Agent 若推理错误，会污染主投影，因此 immutable events 必须保留作为可重建真源。

重复事件： Agent 重试 push 时可能重复创建 event，因此 event 必须有稳定唯一 ID，并按 ID 幂等处理。

事件粒度失控： 如果每个小动作都生成 event，未来目录会迅速膨胀，所以仍应坚持“一个可交付单元才写一次”。

敏感信息泄露： immutable event 一旦进入 Git 历史很难真正消除，因此凭证/key 绝不能写入 event、STATE、日志或 commit，这与你目前协议红线一致。
github.com

需确认（拿不准、需要拍板的点）

**当前是否增加 UPDATES/？**我的建议是“加”，它用极小复杂度解决了最危险的 STATE 静默丢失问题；如果你追求绝对最简，则至少必须增加“pull 后重读 + 保留式 STATE 更新 + push 失败重试”三条规则。

**STATE.md 中“已完成（最近）”保留多少？**建议拍板一个明确窗口，例如“最近 5–10 个交付单元”，否则不同 Agent 会自行决定什么该删。

**DECISIONS 是否真的要求永久单文件 append-only？**如果“一页纸”是硬约束，我建议定义为“当前阶段保持 append-only；达到一页上限后归档，未来由 decision events 保存永久历史”。

**未来 Memory Agent 是否拥有 STATE/DECISIONS 唯一写权？**我建议“是”；普通 Agent 只创建 immutable event，否则引入 Memory Agent 后仍然保留多写者，架构收益会大幅下降。

我的首选演进路线是：现在：4 文件 + UPDATES 保险层 → 达到明显并发冲突后：immutable events + Memory Agent，而不是现在提前建设完整“每 Agent 分记忆”系统。
