结论

建议把“能力值”和“证据可信度”拆开：能力 unknown fail-open，计费 unknown fail-closed。Dots3 不自动突破客户端 token 预算，改做请求形态降权 + 非流式 length+空正文 预提交 failover；真实探针独立白名单运行，永不混入 0-real-API 测试。

优化后方案
1. 能力登记表：从 bool 升级为「tri-state + evidence」

不要把 schema 做成复杂知识库；最小扩展到每个 capability 有这 6 个字段即可：

JSON
{
  "models": {
    "dots3-note-prev": {
      "tools": {
        "value": true,
        "source": "live_probe",
        "confidence": "high",
        "verified_at": "2026-08-29T00:00:00Z",
        "method": "tools+tool_choice_required",
        "ttl_s": 2592000
      },
      "vision": {
        "value": null,
        "source": "legacy_unverified",
        "confidence": "low",
        "verified_at": null,
        "method": null,
        "ttl_s": 0
      }
    }
  }
}

其中 value = true | false | null 就是 tri-state；null 明确表示“不知道”，绝不能再拿 false 表示“没测过”。

建议只允许这些 source：

live_probe          真实最小探针成功/确定失败
traffic_observation 用户真实流量中得到的确定证据
vendor_doc          厂商明确声明
operator_verified   人工核验后登记
inferred            推断
legacy_unverified   旧表迁移、来源不明

有效值不要简单等同于 value，而要计算 effective_value：

value=true
  + evidence 未过期
  + confidence=high
    => effective=true

value=false
  + source ∈ {live_probe, traffic_observation, vendor_doc, operator_verified}
  + confidence=high
  + evidence 未过期
    => effective=false

其它任何组合
    => effective=unknown

因此 PR#2 的原则不需要推翻，只需精确定义：

effective=false  -> capability_mismatch，skip
effective=true   -> :contentReference[oaicite:1]{index=1}:contentReference[oaicite:2]{index=2}
::contentReference[oaicite:3]{index=3}
