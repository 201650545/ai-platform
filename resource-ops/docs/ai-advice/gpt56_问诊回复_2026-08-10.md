# 结论（一页以内总评）

整体方向成立，但当前方案更像“资源资产台账 + 本地执行器”，距离真正稳定的“AI 自助资源运营系统”还差三个关键抽象：**资源能力、凭证实例、执行状态**。

最重要的架构调整是：**不要把“免费资源大汇总”同时当资源目录、密钥池、额度状态、执行配置和验证状态使用。** 18 个字段已经出现职责混杂。建议把“资源定义”和“可调用实例”分离：资源表描述“这是什么、怎么调用”，资源实例/凭证池表描述“我手上具体有哪些可用调用入口、额度多少、当前是否可调度”。这样同一模型、多厂商、多账号、多 Key 的轮换才不会把表2越做越复杂。

本地调度器采用 **本地常驻进程 + OpenAI-compatible/base\_url 代理层** 是最简、最有长期价值的形态。上层 Agent 永远只调用一个本地入口；代理内部根据“模型必须一致、质量等级不可降低、额度未耗尽、凭证有效”等硬规则选路由。不要让 Agent 自己决定换 Key 或厂商，否则“透明轮换、不降质”无法形成可审计保证。

Open CLI 不应该直接承担工作流状态管理。它应只是一个“浏览器执行器”。真正闭环应是：**任务生成 → 任务领取 → 执行 → 证据记录 → 状态机判定 → 飞书原子回写**。避免重复验证不能只依赖日志表，需要在资源/实例侧增加 `next_verify_at / verification_status / verification_fingerprint / lease` 等字段。

安全上，“表内只存凭证 ID”是正确起点，但最大的剩余风险不是数据库，而是**日志、命令行参数、浏览器页面、截图、剪贴板、异常栈、代理请求日志、GitHub JSON、模型上下文**。整个体系应采用“敏感信息默认不可观测”，而不仅是“不可入飞书”。

GitHub Pages 公开 JSON 可以作为早期“只读问诊桥”，但不应成为系统事实源，也不适合发布完整运营数据。它更适合作为**脱敏后的 read model / snapshot**。长期建议由一个本地或云端的只读 API 输出经过字段白名单过滤的视图。

画布中应优先做**可视化运营驾驶舱**，而不是 AI 搜索聚合。搜索能力很容易被现有搜索工具替代；“当前哪些资源可用、为什么被停、额度怎样、最近哪些失败”才是这套系统独有且能快速发现故障的价值。

如果目标是尽快产生价值，第一闭环不应先追求“AI 自动调研、自动领取所有免费资源”，而应先做到：

**一个模型 → 两个真实 Key/厂商 → 本地统一 endpoint → 自动轮换 → 额度停止 → 飞书状态同步 → 可审计日志。**

这个闭环跑稳以后，再把浏览器自动领取、AI 调研、公开问诊桥接进去。

# 建议方案（逐问题给，可改动我原来的设计）

## 1\. 多维表格：4 张表是否最优？免费资源表是否够「AI 可执行」？

**结论：4 张表作为 MVP 可以，但不是长期最优；表2目前“不完全 AI 可执行”。建议增加第 5 张“资源实例/调用池”表。**

当前表2混合了两类本质不同的数据：

-   **资源定义**：平台、endpoint、模型、请求模板、获取方式。

-   **资源实例状态**：凭证ID、剩余额度、账号、失效状态。


例如“OpenAI-compatible 某模型”是一个能力定义，而“账号A的Key1”“账号B的Key2”是两个实例。继续混在一张表里，会在多账号、多 Key、多厂商时快速出现重复字段和更新冲突。

建议调整为：

**表2：资源/能力规格表**

保留：

`resource_id / provider / category / endpoint_type / protocol / model_capabilities / request_schema / response_schema / auth_scheme / quality_tier / acquisition_method / docs / verification_policy`

其中不要保存实时额度。

增加：

`canonical_capability_id`

例如：

`llm:claude-sonnet-x`

它用于声明多个厂商入口提供的是不是**同一个允许互换的能力**。

**新增表5：资源实例 / Credential Pool**

建议字段：

`instance_id`
`resource_id`
`account_id`
`credential_id`
`provider`
`endpoint_override`
`model_mapping`
`status`
`quota_total`
`quota_remaining`
`quota_reset_at`
`rate_limit`
`priority`
`last_success_at`
`last_failure_at`
`failure_count`
`cooldown_until`
`last_verified_at`
`next_verify_at`
`verification_fingerprint`

这样调度器真正读取的是表5，本地凭证值仍由 `credential_id` 映射。

### 密钥池是否应拆独立表？

**应该。**

尤其你的要求是“同模型多厂商轮换”，这是一个明确的一等领域对象，不应藏在资源表若干行之间。

不过我不建议再增加一张纯“Key 表”；更合理的是上面的**资源实例表**。它既表达 Key，也表达账号、额度、厂商 endpoint 和实例状态。

此外建议增加一个调度策略概念：

`routing_group_id`

例如：

`claude-sonnet-prod`

组内成员只能是符合以下条件的实例：

`canonical_capability_id` 相同
`quality_tier` 相同
满足上下文长度等最低规格
没有被人工禁止

这样才能真正落实“不换模型、不降质”。

### 表4日志能否支撑避免重复验证？

**仅靠日志不能。**

日志适合回答“发生过什么”，不适合回答“现在是否应该再执行”。

需要在资源实例中维护物化状态，例如：

`last_verified_at`
`next_verify_at`
`verification_status`
`verification_version`

再生成一个验证指纹：

`fingerprint = hash(endpoint + model + request_template_version + relevant_config)`

只有以下任一情况出现才重新验证：

-   到了 `next_verify_at`

-   fingerprint 改变

-   最近调用真实失败

-   凭证被更新

-   人工强制验证


另外必须加入**任务幂等键**：

`idempotency_key = task_type + instance_id + verification_version`

否则两个 Agent 很容易同时验证同一个资源。

## 2\. 调度器形态：本地进程 + base\_url 代理是不是最简可靠？

**是，而且建议把它作为整个系统最先稳定下来的核心。**

推荐形态：

`Agent / IDE / CLI`
↓
`localhost AI Gateway`
↓
`Router`
↓
`Credential Resolver`
↓
`Provider Adapter`
↓
`厂商 API`

上层只看到类似：

`http://127.0.0.1:xxxx/v1`

并使用逻辑模型名，例如：

`claude-sonnet-approved`

而不是直接看到各厂商真实模型名。

调度器内部应做到：

**路由条件先过滤，再排序，而不是“失败了随便换一个”。**

先筛选：

`capability_match = true`
`quality_tier >= required`
`status = available`
`quota_remaining > safety_margin`
`cooldown_until < now`

然后按：

额度到期时间、剩余额度、优先级、成本等排序。

建议不要第一版就引入复杂服务发现、Redis、消息队列。

MVP 足够：

-   Python / Go / Node 单进程

-   SQLite

-   本地 JSON/系统钥匙串保存凭证

-   飞书负责资产与人工可视化

-   SQLite负责高频运行态


这里有一个重要调整：

**飞书不要承担实时额度计数。**

每请求一次就写飞书，延迟、API 限流和一致性都会成为问题。

更合理：

`本地 SQLite = runtime source of truth`

每隔一段时间或发生重要状态变化时：

`同步摘要 → 飞书`

飞书仍是“资源配置唯一真源”，但运行时计数不必成为强一致事实源。

## 3\. Open CLI 与飞书回写闭环怎么做可靠？

不要设计成：

`AI → Open CLI → 操作网页 → AI想起来后写飞书`

建议设计成正式任务状态机：

`PENDING`
→ `LEASED`
→ `RUNNING`
→ `SUCCEEDED | FAILED | NEEDS_HUMAN`

任务执行前，Agent 必须先领取一个 lease：

`leased_by`
`lease_until`

其他 Agent 看到未过期 lease 不再执行。

每次任务还需要：

`task_id`
`idempotency_key`
`attempt_no`
`input_version`

执行结束后，不让 Open CLI 自己“自由描述结果”，而是返回结构化结果，例如：

JSON

```
{  "status": "SUCCEEDED",  "resource_id": "...",  "changes": {    "quota": "...",    "status": "available"  },  "evidence": {    "final_url": "...",    "page_title": "...",    "observed_text_hash": "..."  }}
```

注意 evidence 应尽量存**哈希、页面标识和脱敏摘要**，而不是把整个页面/截图上传飞书。

然后由一个专门的 **Writer** 完成飞书回写。

最好实行单写者原则：

`多个Agent可执行`
但
`只有一个状态写入模块`

这样能显著减少竞争覆盖。

领取类任务还建议有：

`claim_status = unknown / eligible / claimed / unavailable / human_required`

避免“领取成功”和“资源验证成功”混为一个状态。

## 4\. 画布两功能优先级？

优先级建议：

**第一：HTML 运营可视化。**
**第二：AI 搜索聚合。**

因为你的体系真正缺的不是“又一个搜索入口”，而是可观测性。

第一版驾驶舱只需要回答六个问题：

-   当前有多少可调用资源？

-   哪些核心模型还有备用实例？

-   哪些额度即将耗尽？

-   最近24小时哪些实例自动停用了？

-   哪些验证失败/需要人工？

-   哪些资源超过验证期限？


甚至不必一开始上复杂图表。

一个非常有价值的指标是：

**Coverage**

例如：

`Claude Sonnet：3/4 instances healthy`

比展示“共有100个免费资源”有价值得多。

AI 搜索聚合放后面，主要用于发现“值得加入规格库的新资源”，最终结果仍必须走：

`发现 → 候选 → 验证 → 入库`

不能让搜索结果直接进入可执行池。

## 5\. 安全模型还有哪些泄漏路径？

凭证值只保存在本地是正确设计，但建议建立一个明确原则：

**Secret 可以进入执行平面，但不能进入观察平面。**

主要遗漏风险如下：

-   CLI 命令行参数可能被 shell history 或进程列表记录。

-   HTTP proxy access log 可能记录 Authorization header。

-   exception / stack trace 可能打印完整请求。

-   浏览器自动化可能把 token 出现在 DOM、URL、下载文件或页面截图中。

-   AI Agent 的上下文可能无意包含 credential 或兑换码。

-   clipboard 会成为隐形 Secret transport。

-   `.env`、credentials.json 可能被 Git 自动提交。

-   crash dump、debug dump、HTTP trace 可能保存密钥。

-   GitHub Pages JSON 字段扩展后可能无意公开账号或内部资源信息。

-   飞书日志的“错误信息”字段最危险，厂商 SDK 经常会输出 request headers。

-   Prompt injection 页面可能诱导 Open CLI 把本地信息复制到网页。

-   浏览器扩展本身可能拥有页面读取权限。


具体措施建议至少包括：

`secret redaction middleware`

统一拦截：

`Authorization`
`api_key`
`token`
`cookie`
已知 credential values

并禁止在日志中出现。

进一步建议：

凭证文件权限限制
使用 OS keychain 优于裸 JSON
每个 provider 使用最小权限 token
本地 gateway 默认只监听 `127.0.0.1`
管理 API 与模型调用 API 分开
增加域名 allowlist
Open CLI 禁止上传本地文件，除非任务明确授权
浏览器遇到 MFA、验证码、身份确认、购买/支付等立即 `NEEDS_HUMAN`

特别重要：

**“AI 以本人身份”不能等价于“AI 拥有本人全部浏览器权限”。**

执行器仍应限制可以访问的域名和动作类别。

## 6\. GitHub 公开 JSON 作为问诊桥是否高效？

**作为 MVP 很高效，作为长期架构不够安全也不够灵活。**

优点非常明显：

静态
廉价
缓存好
连接器容易读
AI 容易理解

所以我不建议立刻移除。

但应该把它定义为：

**Public Read Model**

而不是“飞书数据库镜像”。

建立一个 export 层：

`飞书`
→ `Exporter`
→ `字段白名单`
→ `脱敏/聚合`
→ `resource_catalog.public.json`
→ GitHub Pages

公开 JSON 中只放：

资源能力
平台
状态
公开 endpoint 信息
模型
免费额度描述
验证日期
健康度

不要放：

账号标识
credential\_id
手机号绑定状态
内部错误信息
内部路由优先级
任务记录
本机结构

甚至 `credential_id` 也没有必要公开，因为它虽然不是秘密，却会泄漏内部资产结构。

长期更优的方式是：

`read-only query API / MCP server`

允许 AI 问：

`哪些Claude Sonnet等价实例当前healthy？`

而不是每次拉完整 JSON。

但在资源规模还不大之前，不值得过早建设。

所以推荐：

**MVP：静态 JSON。**

**规模化以后：查询型 API/MCP。**

# 风险（每条一句话）

-   飞书同时承担配置与高频运行态，会造成一致性、延迟和 API 限流问题。

-   资源定义与 Credential 实例不拆分，规模增加后会导致重复数据和调度逻辑失控。

-   仅靠任务日志去重无法阻止并发 Agent 重复验证或重复领取。

-   “同模型”名称相同并不必然意味着上下文、工具调用、推理能力和输出质量真正等价。

-   若 provider fallback 没有严格 capability gate，“自动轮换”很容易悄悄演变成质量降级。

-   浏览器自动化面对验证码、MFA、风控页面时可靠性天然低于 HTTP API。

-   Open CLI 如果拥有无限浏览器权限，会显著放大网页 Prompt Injection 风险。

-   错误日志和 debug trace 比数据库本身更容易泄漏 API Key。

-   GitHub 公开 JSON 一旦字段白名单失控，会形成长期可抓取的信息泄漏面。

-   凭证ID虽然不是 Secret，但公开后仍可能暴露资产数量、账号结构和供应商关系。

-   quota 数据来自本地估算时可能与厂商真实账单存在偏差。

-   多进程调度如果没有 lease/事务，会出现同一额度被并发超用。

-   浏览器领取资源可能违反某些厂商的活动、账号或自动化规则，需要逐平台确认。

-   免费资源本身变化快，缺乏过期策略会导致规格库迅速积累“僵尸资源”。

-   若从一开始追求全平台自动领取，开发复杂度会远高于核心调度器产生的实际收益。

# 实施步骤（编号，可执行）

1.  **新增资源实例表**，将表2中的 `凭证ID、已用剩余、关联账号` 等实例字段逐步迁出。

2.  给资源表增加 `canonical_capability_id`、`quality_tier`、`verification_policy`，明确哪些入口允许互为替代。

3.  给实例表增加 `instance_id、credential_id、quota_remaining、quota_reset_at、cooldown_until、last_verified_at、next_verify_at、verification_fingerprint`。

4.  在本地建立 SQLite，创建 `resources / instances / usage / tasks / events` 最小数据结构。

5.  开发 localhost gateway，第一版只兼容一个最常用的 API 协议和一个模型。

6.  实现 credential resolver：仅在真正向厂商发送请求前，根据 `credential_id` 本地取 Secret。

7.  实现 routing gate：模型能力、质量等级、状态、额度全部通过后，实例才进入候选集合。

8.  实现硬停止规则，例如额度达到安全阈值立即把 instance 标为 `EXHAUSTED`，不得再尝试。

9.  准备两个真实实例做端到端测试，人工把 A 调成不可用，确认请求自动切到 B 且逻辑模型完全不变。

10.  在 gateway 加统一 redaction middleware，禁止凭证、Cookie、Authorization header 进入日志。

11.  所有网关日志改为结构化事件，只保存 `request_id、instance_id、model、latency、tokens、result` 等非秘密字段。

12.  开发飞书 sync worker，配置同步采用 `飞书 → SQLite`，运行态按周期或事件 `SQLite → 飞书`。

13.  给任务表增加 `idempotency_key、leased_by、lease_until、attempt_no`，实现事务式任务领取。

14.  自动验证任务生成规则改为基于 `next_verify_at + fingerprint`，而不是扫描历史日志判断。

15.  实现一个纯 HTTP provider 的完整 `验证 → 更新实例 → 日志` 闭环。

16.  开发最小运营页面，优先显示 capability coverage、healthy instances、quota、失败任务和待人工任务。

17.  将 Open CLI 包装成 executor，只接受结构化任务，不允许它直接修改任意飞书字段。

18.  给 Open CLI 建立 domain allowlist 和人工停机条件，验证码、MFA、支付、身份确认全部转 `NEEDS_HUMAN`。

19.  为网页执行结果定义固定 schema，只允许结构化结果进入 Writer。

20.  给浏览器执行加入证据摘要和页面 hash，但默认不保存包含账号信息的整页截图。

21.  建立 Public Exporter，对公开 JSON 使用严格字段白名单，而不是直接导出飞书记录。

22.  将 GitHub Pages JSON 定义成只读快照，明确禁止出现 credential\_id、账号ID、手机号、错误详情和内部路由信息。

23.  当公开 JSON 拉取开始明显低效时，再升级到只读查询 API 或 MCP，不提前建设。

24.  最后再接入 AI 搜索，使搜索结果先进入 `CANDIDATE` 状态，验证成功后才能成为 `AVAILABLE`。

25.  建立最终核心指标：不是“收集多少资源”，而是 **核心 capability 的健康实例数、自动恢复率、人工介入率和误路由次数**。
