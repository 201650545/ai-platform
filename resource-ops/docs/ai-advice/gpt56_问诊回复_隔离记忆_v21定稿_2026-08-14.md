四、单条 inbox 文件格式

建议：

YAML
---
schema: inbox-v1
id: I-20260814T083001-A7F2C941
captured_at: 2026-08-14T08:30:01-04:00
capture_scope: session:8f3c2a
project_hint: UNKNOWN
routing_basis: none
kind_hint: auto
candidate_project:
candidate_reason:
---

用户决定以后这个课程都按照这种结构组织。

字段语义：

字段	要求	含义
id	必须、不可变	staging 唯一 ID
captured_at	必须、不可变	带时区 ISO 时间
capture_scope	必须、不可变	origin 隔离边界
project_hint	必须	canonical project 或 UNKNOWN
routing_basis	必须	为什么能确定 project
kind_hint	必须	auto/state/decision
candidate_project	可选	纯语义推断候选，不构成路由权限
candidate_reason	可选	候选原因
body	必须	最小可复用事实，不是聊天全文

capture_scope 建议采用：

session:<opaque-id>
task:<opaque-id>

它不是 project_id。

它的主要用途就是落实你已经拍板的：

当前项目 Agent 可以看到“当前会话自己产生的 UNKNOWN”，但不能看到别的 UNKNOWN。

五、inbox/META.json

只存系统水位，不存记忆内容：

JSON
{
  "schema": "inbox-meta-v1",
  "last_settle_date": null,
  "last_settle_at": null
}

这里有一个实现细节建议：

last_settle_date 只有在本轮整理之后已经不存在“昨天及更早的待处理条目”时才推进到 today。

例如：

teaching 已整理
courseware 已整理
但是还有 3 条昨天的 UNKNOWN

那么：

last_settle_date

不要更新为今天。

否则 teaching 的一次局部 settle 会错误地掩盖仍未整理的 UNKNOWN。

1. capture
接口
Bash
python scripts/memory.py capture \
  --capture-scope <scope> \
  [--project-hint <project|UNKNOWN>] \
  [--routing-basis explicit|task|workspace|alias|none] \
  [--kind-hint auto|state|decision] \
  --content <text>

最常见：

Bash
python scripts/memory.py capture \
  --capture-scope session:8f3c2a \
  --content "以后这个课程统一用该结构"

等价于：

project_hint = UNKNOWN
routing_basis = none
kind_hint = auto

已确定项目：

Bash
python scripts/memory.py capture \
  --capture-scope session:8f3c2a \
  --project-hint courseware \
  --routing-basis explicit \
  --kind-hint decision \
  --content "课件统一使用 16:9"

如果：

project_hint != UNKNOWN

必须调用现有 resolve_project() 做 canonicalize。

因此：

Bash
--project-hint ppt

可以根据 MEMORY.json aliases 转成：

courseware

Bash
--project-hint abc-unknown-project

必须失败。

project_hint = UNKNOWN

不调用 resolve_project()，因为 UNKNOWN 是 staging 状态，不是项目。

Secret guard

capture 必须在 write_text() 之前检查内容。

现有 pre-commit 已扫描 sk-、Google API key、Bearer token、app_token、app_secret 等模式，但它是在 staged content 阶段才阻止 commit。v2.1 要把同一原则提前到 capture ingress。

3. settle-plan

这是只读规划器，不是写入器。

接口
Bash
python scripts/memory.py settle-plan --all

或：

Bash
python scripts/memory.py settle-plan --project teaching

建议支持：

Bash
--json

完整形式：

Bash
python scripts/memory.py settle-plan \
  (--all | --project <id>) \
  [--json]
分类状态

每个 item 只能落入：

READY
NEEDS_KIND
CANDIDATE
UNRESOLVED

判定：

project_hint known + kind known
→ READY

project_hint known + kind=auto
→ NEEDS_KIND

project_hint UNKNOWN + candidate_project exists
→ CANDIDATE

project_hint UNKNOWN + no candidate
→ UNRESOLVED

例如：

READY
I-001 → courseware / decision

NEEDS_KIND
I-002 → teaching / auto

CANDIDATE
I-003 → UNKNOWN
candidate=courseware

UNRESOLVED
I-004 → UNKNOWN

注意：

CANDIDATE 永远不能被 settle 自动升级。

这正是你拍板的“纯内容判断只能 candidate”。

settle-plan --all 是 settler 批量整理 UNKNOWN、最后一次性向用户提问的主要入口。

4. resolve

这是 staging metadata 的人工/Router 消歧入口。

A. UNKNOWN → 正式项目
Bash
python scripts/memory.py resolve \
  --id I-20260814T083001-A7F2C941 \
  --project courseware \
  --basis user

建议允许的 basis：

user
explicit
task
workspace
alias

不允许：

semantic

作为正式 resolution basis。

如果是语义推理，只能走 candidate。

B. 设置 kind
Bash
python scripts/memory.py resolve \
  --id I-xxx \
  --kind decision

也可以一次完成：

Bash
python scripts/memory.py resolve \
  --id I-xxx \
  --project courseware \
  --basis user \
  --kind decision
C. 只记录 semantic candidate
Bash
python scripts/memory.py resolve \
  --id I-xxx \
  --candidate-project courseware \
  --reason "内容提到 PPT 页面和动画，但缺少确定性项目上下文"

处理后必须仍然是：

YAML
project_hint: UNKNOWN
candidate_project: courseware

而不能变成：

YAML
project_hint: courseware

这条应机械保证。

D. 确认“已经被现有记忆覆盖”

推荐补这个分支，避免 consolidation 制造重复：

Bash
python scripts/memory.py resolve \
  --id I-xxx \
  --covered-by S-20260814-18 \
  --project memory-system \
  --reason "已有状态项完整覆盖"

结果：

不新增 STATE
不新增 DECISION
移动到 settled
生成 receipt
E. discard
Bash
python scripts/memory.py resolve \
  --id I-xxx \
  --discard \
  --reason "一次性过程信息，无跨会话复用价值"

这可以立即完成：

pending → settled
receipt disposition=discarded

不需要 project_id。

这与当前 AGENTS 的记忆写入原则一致：中间探索、一次性、不再复用的内容本来就不应进入正式共享记忆。
GitHub

十二、lazy daily consolidation 定稿

仓库现有全局决策明确拍板：

工作模型是按需调度，不做定时提醒/汇报平台。
GitHub

AGENTS §4 也重复了“不搭定时提醒/汇报平台”。
GitHub

因此 v2.1 不增加：

cron
Windows Task Scheduler
GitHub Actions schedule
daemon
后台服务

due 条件定稿为：

daily_due
    = 存在 captured_date < today 的 pending
      且本轮 consolidation 尚未清掉这些 overdue items

count_due
    = pending_count >= 20

unknown_due
    = unknown_count >= 5

settle_due
    = daily_due OR count_due OR unknown_due

用户显式说：

整理记忆

则无需判断阈值，直接：

status --settler
settle-plan --all

十六、R1'～R16 协议条文定稿

下面这版我建议直接替换 global/RULES.md 的宪法部分。

## 16 条宪法（v2.1）

R1'. 正式项目记忆的读取、搜索、写入与巩固必须携带明确 project_id；
     staging capture 不要求先确定 project_id，但必须携带 capture_scope，
     project_hint 可以为已注册项目或 UNKNOWN。

R2.  正式记忆仍坚持 Routing before Retrieval：
     project_id 必须在读取项目正式记忆之前唯一确定。
     staging capture 是唯一允许发生在项目路由完成之前的持久化操作，
     但 staging 内容不得因此获得正式项目记忆权限。

R3.  普通项目 Agent 默认只能读取：
     global + 当前项目正式记忆 + 当前项目 staging。
     如提供当前 capture_scope，可额外读取该 capture_scope 自己产生的 UNKNOWN。
     不得读取其他项目 staging 或其他来源 UNKNOWN。

R4.  跨项目读取必须显式声明 read_scope/imports。
     UNKNOWN 全量扫描不属于普通跨项目读取能力；
     只有 settler/memory-router 在 consolidation 场景下允许执行。

R5.  一次正式记忆操作只能有一个 write_scope。
     settle 必须指定且只能写一个 project_id；
     禁止一次 settle 同时修改多个项目。
     staging capture/resolve 属于 staging write_scope，不得同时夹带项目正式写入。

R6.  Agent 不得指定实际记忆文件路径。
     正式记忆路径由 Router 根据 project + kind 决定；
     staging 路径由 Router 根据 inbox id / capture date 决定。

R7.  Fail Closed：
     正式 project scope 无法唯一确定时，宁可不读、不写、不 settle，绝不猜。
     纯内容语义判断只能形成 candidate_project，
     不得直接把 UNKNOWN 提升为正式 project_id。

R8.  Archive 与 settled staging 均属于冷历史，默认不可见。
     只有显式历史检索、审计或 consolidation 追溯时才能进入。
     普通 Agent 不得把冷历史作为默认上下文加载。

R9.  CHANGELOG、项目索引、staging receipt、META 等机械账本由脚本维护，
     Agent 不直接编辑。
     正式 memory write/settle 必须沿用脚本自动 CHANGELOG 记录。

R10. Staging 是 Quarantined Candidate Memory，不是正式共享记忆。
     UNKNOWN 表示“归属尚未确定”，绝不表示 GLOBAL、PUBLIC 或所有项目可读。

R11. 普通项目 Agent 对 staging 的可见范围严格为：
     project_hint == current_project
     +（可选）capture_scope == current_scope 且 project_hint == UNKNOWN。
     默认禁止扫描全部 UNKNOWN。

R12. 只有 settler/memory-router 可以全量扫描 UNKNOWN 并执行分类。
     确定性证据优先级为：
     用户明确指定 > 已绑定 task/Skill > workspace/path >
     MEMORY.json alias。
     纯内容推理只能给 candidate；
     存在歧义时继续 UNKNOWN，并累积后批量询问用户。

R13. Consolidation 必须先判断“值不值得成为正式记忆”。
     staging candidate 可以被 promote、判定已有记忆 covered、或 discard。
     project/kind 未解决的 item 必须继续留在 pending；
     禁止为了清空 inbox 而强行分类或写入。

R14. Consolidation 采用 Lazy Daily Consolidation，不建立 cron、
     GitHub Actions schedule、daemon 或其他定时提醒/汇报平台。
     触发条件为：
     会话/项目启动检查；
     pending >= 20；
     UNKNOWN >= 5；
     用户显式要求“整理记忆”；
     或存在前一日及更早的 pending。
     到期只触发整理流程，不允许绕过 Fail Closed 自动猜测 UNKNOWN。

R15. staging item 在 settle/discard 后不得无痕删除。
     原 candidate 移入 inbox/settled，
     同时生成 receipt 记录 disposition、最终项目、kind、target ID、
     routing basis 与时间。
     settled 内容默认只读；修正通过新的记录完成，不静默篡改历史。

R16. 凭证、API key、token、secret 绝不进入任何 memory/staging 文件或 commit。
     capture 必须在文件落盘之前执行 secret preflight 并 fail closed；
     pre-commit secret guard 继续作为第二道机械防线。

R2-R9 的核心没有被推翻，只是在 staging 出现以后把边界说清楚。当前 v2 原始九条宪法明确包含 Routing before Retrieval、global+当前项目、Single-write、Router 决定路径、Fail Closed、archive 默认不可见以及脚本维护 CHANGELOG/INDEX。
